Middleware runs before the handlers for an event. Throwing from it stops all of them.

```ts twoslash title="src/events/middlewares/SkipMuted.ts"
import {
    EventMiddleware,
    RegisterEventMiddleware,
    Silence
} from '@seedcord/gateway';
import { Events } from 'discord.js';
// ---cut-start---

declare function isMuted(userId: string): Promise<boolean>;
// ---cut-end---

@RegisterEventMiddleware({
    events: [Events.MessageCreate]
})
export class SkipMuted extends EventMiddleware<Events.MessageCreate> {
    public async execute(): Promise<void> {
        const [message] = this.event;

        if (await isMuted(message.author.id)) {
            throw new Silence('author is muted');
        }
    }
}
```

[`@RegisterEventMiddleware`](ref:gateway/RegisterEventMiddleware) takes one options object. An [interaction runs its own chain](/checks/middleware) through [`@RegisterInteractionMiddleware`](ref:core/RegisterInteractionMiddleware), which filters on `{ kinds }`.

## Stopping the event

Any throw stops the event. The class you throw decides what the user sees. With a [`Silence`](ref:core/Silence) the user sees nothing. A reason passed to it goes to a debug log. Anything else goes down the same path that a handler's [throw](/replying/throwing) takes.

That stops one dispatch. The next message runs the chain again from the top.

## Which events it runs for

Whatever you put in `{ events }`, the generic on [`EventMiddleware`](ref:gateway/EventMiddleware) has to list too. Applying the decorator with a mismatch is a compile error. `SkipMuted` above takes one, so [`this.event`](ref:gateway/EventMiddleware.event) is that event's payload.

With several, the payload could be any of them, so `this.event` turns `never`. [`this.eventName`](ref:gateway/EventMiddleware.eventName) returns the event that fired.

```ts twoslash title="src/events/middlewares/CountMessages.ts"
import {
    EventMiddleware,
    RegisterEventMiddleware
} from '@seedcord/gateway';
import { Events } from 'discord.js';
// ---cut---
@RegisterEventMiddleware({
    events: [Events.MessageCreate, Events.MessageDelete],
    priority: 1
})
export class CountMessages extends EventMiddleware<
    Events.MessageCreate | Events.MessageDelete
> {
    public async execute(): Promise<void> {
        const name = this.eventName;
        //    ^?
        this.logger.debug(`${name} fired`);
    }
}
```

Leaving `{ events }` off gives a catchall, which runs on every event that your handlers registered. Drop the generic with it.

```ts twoslash title="src/events/middlewares/Trace.ts"
import {
    EventMiddleware,
    RegisterEventMiddleware
} from '@seedcord/gateway';
// ---cut---
@RegisterEventMiddleware({ priority: 2 })
export class Trace extends EventMiddleware {
    public async execute(): Promise<void> {
        this.logger.debug(`${this.eventName} reached the chain`);
    }
}
```

Write one class per event when you need each payload shape.

## Order

`priority` decides the order, with lower running first. It takes any finite number and defaults to `0`. That puts `SkipMuted` first at `0`, then `CountMessages` at `1`, then `Trace` at `2`.

Two middlewares at the same priority run in the order that seedcord loaded them. Give anything order-dependent its own number.

## Passing a value along

Every handler for one event shares a single bag with the chain ahead of it. A middleware writes a value there, then each handler reads that same value back.

```ts twoslash title="src/events/middlewares/Locale.ts"
import '@seedcord/gateway';

import {
    EventMiddleware,
    RegisterEventMiddleware
} from '@seedcord/gateway';
import { Events } from 'discord.js';

declare module '@seedcord/gateway' {
    interface DispatchState {
        locale: string;
    }
}
// ---cut---
@RegisterEventMiddleware({ events: [Events.MessageCreate] })
export class Locale extends EventMiddleware<Events.MessageCreate> {
    public async execute(): Promise<void> {
        const [message] = this.event;
        const guildLocale = message.guild?.preferredLocale;

        this.dispatch.set('locale', guildLocale ?? 'en-US');
        await Promise.resolve();
    }
}
```

Declaring the key and reading it back works the same way it does on [an interaction dispatch](/checks/dispatch-context). The one difference is scope, since one event shares its bag across every handler it runs while an interaction has a single handler.

## After the event

When the event finishes, `after()` runs on every middleware whose `execute()` began, newest first. That includes a middleware that throws, since seedcord records it before `execute()` runs. The ones behind it never started and get nothing.

A middleware that stopped the event reaches its `after()` the same way. Use it to release whatever `execute()` held open.

```ts twoslash hovers title="src/events/middlewares/Timing.ts"
import {
    EventMiddleware,
    RegisterEventMiddleware
} from '@seedcord/gateway';

import type { EventDispatchResult } from '@seedcord/gateway';
// ---cut---
@RegisterEventMiddleware()
export class Timing extends EventMiddleware {
    private startedAt = 0;

    public async execute(): Promise<void> {
        this.startedAt = performance.now();
        await Promise.resolve();
    }

    public override async after(
        result: EventDispatchResult
    ): Promise<void> {
        const elapsed = Math.round(
            performance.now() - this.startedAt
        );

        this.logger.debug(
            `${this.eventName}: ${result.handlers.length} in ${elapsed}ms`
        );
        await Promise.resolve();
    }
}
```

`after()` is optional on the base, which means an implementation marks itself `override`. TypeScript reports a missing one.

[`EventDispatchResult`](ref:core/EventDispatchResult) reports how the event ended, in two parts. `outcome` describes the chain alone, so a handler that throws still leaves it `handled`. `handlers` holds one entry per handler that ran, each carrying its class name and its own outcome.

That list is empty exactly when the chain stopped the event. A throw inside `after()` reaches the log and stops there, which leaves the rest of the chain running.

## Where middleware lives

Middlewares live under `bot.events.middlewares`. The key is optional in case you don't want middlewares.

```ts twoslash title="src/bot.ts"
import { resolve } from 'node:path';

import { Seedcord } from '@seedcord/gateway';
import { GatewayIntentBits } from 'discord.js';

const rest = {
    interactions: { path: null },
    commands: { path: null }
} as const;
// ---cut---
export const seedcord = new Seedcord({
    bot: {
        ...rest,
        clientOptions: { intents: [GatewayIntentBits.Guilds] },
        events: {
            path: resolve(import.meta.dirname, './events'),
            middlewares: resolve(
                import.meta.dirname,
                './events/middlewares'
            )
        }
    },
    subscribers: { path: null }
});
```

A class without `@RegisterEventMiddleware` loads and never runs, the same way a handler without `@RegisterEvent` does. The `@seedcord/middleware-missing-register-decorator` rule reports it.

<Callout type="warning">

Middleware runs only when a handler is about to run. seedcord checks for a handler left to run before it starts the chain. So a catchall middleware skips any event that nothing handles, and any event whose handlers were all registered `once` and have already run.

</Callout>

<Callout type="transport" only="gateway">

`@RegisterEventMiddleware` and `EventMiddleware` ship on `@seedcord/gateway`. An http bot has no client events to run them on.

</Callout>

[Message events](/events/messages) carry some rules that no middleware can work around.

---
title: The framework's bus keys
description: Every deploy, every dispatch, and every fault already publishes a key you can subscribe to.
---

seedcord publishes its own keys onto `core.bus`. Subscribe to them with [`@Subscribe`](ref:core/Subscribe) or `core.bus.on`, the same way you subscribe to your own. [The bus](/events/bus) shows why publishing one fails to compile.

The `where` column names the transport that publishes each one.

{/* prettier-ignore-start */}

| key | where | fires when |
| --- | --- | --- |
| `unknownException` | both | a raw throw reaches the fault boundary |
| `handledException` | both | a [`Notice`](ref:core/Notice) with `report` true is caught |
| `unhandledInteractionError` | both | an interaction dispatch throws past the boundary |
| `interactionDispatched` | both | one dispatch settles |
| `responseAttempted` | both | any write through the reply surface |
| `commandsDeployed` | both | a command deploy finishes |
| `anyInteraction` | both | an interaction arrives, before routing |
| `unhandledEventError` | gateway | an event dispatch throws past the boundary |
| `eventDispatching` | gateway | before the handlers for an event run |
| `eventDispatched` | gateway | those handlers settle |

{/* prettier-ignore-end */}

<Callout type="transport">

`anyInteraction` carries a discord.js `Interaction` on gateway and an `APIInteraction` on http. A subscriber that calls a discord.js method on it compiles on gateway and fails on http.

On http it publishes once the request clears Ed25519 verification and the replay checks, so a forged or repeated request never reaches it.

</Callout>

## After a deploy

`commandsDeployed` fires once your bot has told Discord about its commands, including the redeploy that follows a hot reload. The payload carries what Discord accepted.

```ts twoslash title="src/subscribers/DeployLog.ts"
import { Subscribe, Subscriber } from '@seedcord/gateway';

@Subscribe('commandsDeployed')
export class DeployLog extends Subscriber<'commandsDeployed'> {
    public async execute(): Promise<void> {
        const { global, guilds } = this.data;

        this.logger.info(`${global.length} global commands live`);

        for (const [guildId, commands] of Object.entries(guilds)) {
            this.logger.info(`${commands.length} in ${guildId}`);
        }
    }
}
```

`global` and the values in `guilds` are `APIApplicationCommand[]` straight from Discord, so each command carries the id that Discord assigned.

## Watching everything come in

`anyInteraction` fires before seedcord routes an interaction anywhere. `eventDispatching` fires for client events, ahead of the handlers.

```ts twoslash title="src/subscribers/Trace.ts"
import { Subscribe, Subscriber } from '@seedcord/gateway';
// ---cut---
@Subscribe('eventDispatching')
export class Trace extends Subscriber<'eventDispatching'> {
    public async execute(): Promise<void> {
        const { name, args } = this.data;

        this.logger.debug(
            `${name} arrived with ${args.length} args`
        );
    }
}
```

`name` and `args` narrow together, so a check on `name` gives you that event's own tuple.

<Callout type="warning">

`eventDispatching` fires only for an event that some handler registered, since seedcord attaches a client listener per registered event. It also fires ahead of your middleware, so an event that a middleware later stops has already published here.

</Callout>

`eventDispatched` closes the pair once the handlers settle. Read it for outcomes, and see [the telemetry page](/events/telemetry) for its fields.

## The two unhandled errors

`unhandledInteractionError` and `unhandledEventError` both carry `{ error: Error }` and nothing else. seedcord publishes them when a dispatch throws past the fault boundary. By then it has already caught and answered every ordinary throw, so anything reaching here points at a bug in the framework.

## The fault keys

`unknownException` fires on a raw throw.

{/* prettier-ignore-start */}

| field | type | what it holds |
| --- | --- | --- |
| `uuid` | `UUID` | this fault, and the id the error card shows the user |
| `dispatchId` | `string \| null` | the dispatch it came from, null on a process-level throw |
| `error` | `Error` | the throw itself |
| `origin` | `string` | where it came from, for example `slash:ban` or `event:messageCreate:AutoMod` |
| `guild` | `{ id, name }` | optional, the guild the dispatch ran in |
| `user` | `{ id, username }` | optional, whoever ran it |
| `metadata` | `unknown` | optional. On an event fault it holds the event name, the handler, and the args |

{/* prettier-ignore-end */}

A reported `Notice` thrown from an autocomplete publishes here, since [`FaultSource`](ref:core/FaultSource) covers interactions and events only.

`handledException` fires on a [`Notice`](ref:core/Notice) with `report` true.

{/* prettier-ignore-start */}

| field | type | what it holds |
| --- | --- | --- |
| `uuid` | `UUID` | this fault, and the id the error card shows the user |
| `dispatchId` | `string` | the dispatch that reported it |
| `origin` | `string` | the same shape `unknownException` carries |
| `denial` | [`Notice`](ref:core/Notice) | the Notice itself |
| `source` | [`FaultSource`](ref:core/FaultSource) | where the throw came from, typed per transport |

{/* prettier-ignore-end */}

An event `origin` carries a third segment naming the handler, since one fire runs several of them.

seedcord ships a subscriber for each and registers it for you. Both [post a card to a Discord webhook](/replying/reporting) once you set `UNKNOWN_EXCEPTION_WEBHOOK_URL` and `HANDLED_EXCEPTION_WEBHOOK_URL`. An unset variable leaves that reporter off and warns you about it during boot.

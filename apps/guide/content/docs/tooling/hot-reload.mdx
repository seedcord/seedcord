title: Hot reload
description: Swap a saved file into your running bot with seedcord dev, and see which saves still need a full restart.
---

When you save a file under `seedcord dev`, seedcord unloads that file, imports the fresh copy, and registers its handlers again. Your bot keeps its connection to Discord the whole time, so you can switch back to Discord and test the change immediately.

## What reloads in place

A saved file reloads when it holds one of these.

- an interaction handler or middleware
- a command after you answer `y` to the [refresh prompt](#saving-a-command)
- an event handler (gateway only)
- a bus subscriber
- a plugin that your bot file attaches. seedcord [starts it again](/writing-plugins/hot-reload#saving-the-plugins-own-source) from the saved code
- files a plugin loads itself if the plugin implements `onHmr`. [Reloading in dev](/writing-plugins/hot-reload) shows how

Any other file, like a component or a helper, reloads through the files that import it. Editing a file that none of those groups imports doesn't trigger a reload. Reloading works only in the `development` and `test` modes, so `ENV=staging seedcord dev` never reloads.

## Saving a command

Discord keeps its own copy of each command's name, description, and options, so an edit there has to reach Discord before anyone sees it. When you save a file in your commands folder, the dev terminal lists the changed files and shows this prompt before seedcord sends anything:

```txt output
Commands updated:
- src/commands/Ping.ts
Refresh commands? (y/n)
```

{/* prettier-ignore-start */}

| answer | what happens |
| --- | --- |
| `y` | seedcord reloads the command in the bot, runs [codegen](/tooling/codegen) again, and [deploys](/commands/deployed#when-a-deploy-happens) every scope that changed |
| `n` | Discord and the running bot both keep the old command. Restart the bot to load the change |

{/* prettier-ignore-end */}

A plugin can show the same prompt for files that change your commands, like the [i18n plugin](/plugins/i18n-commands) does for its translation files. [Reloading in dev](/writing-plugins/hot-reload#files-that-change-your-commands) shows how.

## How it works

Node can't unload a module once it has imported it. A plain watcher like `node --watch`, `nodemon`, or `tsx watch` works around that by restarting the process. For a gateway bot that means logging in to Discord again, and Discord limits how many [sessions](https://discord.com/developers/docs/events/gateway#session-start-limit-object) a bot may start per day. `seedcord dev` runs your bot inside Vite's module runner instead, which keeps its own graph of the modules it evaluated. seedcord removes the saved file from that graph and imports it again, inside the process that's already running.

The graph also records which modules imported which, so seedcord reloads the modules that imported your saved file, and the ones that imported those. Saving a component every handler builds therefore updates all of them. Vite's watcher reports each file you save, and its transform step reads your TypeScript and your tsconfig paths. Its message channel passes what the CLI and your bot say to each other, like the restart prompt below.

A few files can't be swapped this way because something read them once when the bot started.

## Files that need a restart

seedcord asks for a full restart when you save one of these since the CLI or the bot reads each of them once at startup:

- a file beside `seedcord.config.ts` named `seedcord.config.*`, `tsconfig*.json`, `package.json`, or a lockfile (`pnpm-lock.yaml`, `package-lock.json`, `yarn.lock`, `bun.lock`, `bun.lockb`)
- a `.env`, `.env.local`, `.env.<mode>`, or `.env.<mode>.local` file beside `seedcord.config.ts`
- on an edge bot, `cloudflare.config.ts`, `.dev.vars`, and `.dev.vars.<mode>`
- the file `instance` points at
- a file that `instance` imports for something other than a plugin, like a `settings.ts` that your bot file reads its config from, and any file that one of those imports
- an image in your [emojis folder](/components#emojis-by-name), added, changed, or deleted

These sit beside the config, so they count even when `root` is `./src`. A `package.json` deeper in the project reloads like any other file. The `build.start` file isn't one of them because `seedcord dev` never loads it.

A plugin that your bot file imports and attaches isn't on this list. When you save it, seedcord stops the running plugin and [starts a new one](/writing-plugins/hot-reload#saving-the-plugins-own-source) from the saved code. If you save it before the bot has finished starting, or the new plugin throws while it starts, seedcord asks for a restart.

After you save one of those, your bot keeps running the old code, and the terminal prints this.

```txt output
Restart required. Press r to restart.
```

Nothing restarts automatically. Press `r` once you're ready to disconnect for a moment.

Your own files can need a restart too. The usual case is a file that opens a connection or computes something once at import since a reload imports it again and repeats that work. `dev.hmr.restart` takes glob patterns. They're relative to `root`, so `./config/**` and `config/**` match the same files. An absolute path works too.

```ts twoslash title="seedcord.config.ts"
import { defineConfig } from 'seedcord';

export default defineConfig({
    root: './src',
    instance: './bot.ts',
    build: { start: './index.ts' },
    dev: {
        hmr: { restart: ['config/**', 'constants.ts'] }
    }
});
```

With this config, saving anything under `src/config/` or `src/constants.ts` needs a restart, and so does saving a file that one of them imports. A plugin can add patterns to the same list with [`registerCriticalFiles`](ref:core/Plugin.registerCriticalFiles).

## A file that throws on import

Typos happen. If a file throws while seedcord imports it, its handlers would disappear and the route would stop answering until you fixed it. seedcord keeps the last working version of those handlers registered instead.

```txt output
Rolled back ./src/handlers/Ping.ts to the last-good version
```

`Ping` keeps answering with its old code until your next working save replaces it, so a quick test in Discord can pass against the version you meant to replace. A new file that has never loaded doesn't have a last working version and doesn't register anything until it imports cleanly.

Setting `dev.hmr.rollback` to `false` turns rollback off. seedcord then removes a broken file's handlers, so the route stops answering until you fix it.

```ts twoslash title="seedcord.config.ts"
import { defineConfig } from 'seedcord';
// ---cut---
export default defineConfig({
    root: './src',
    instance: './bot.ts',
    build: { start: './index.ts' },
    dev: {
        hmr: { rollback: false }
    }
});
```

## Type errors while you work

`seedcord dev` runs your code without checking types, so a type error only reaches you when your editor shows it. A handler with a wrong type still loads and can fail at runtime. Turning on `dev.hmr.typecheck` runs `tsc --watch` alongside the bot and reports what it finds on the `tsc` channel, which you can [filter to](/tooling/dev#filtering-the-log).

```ts twoslash title="seedcord.config.ts"
import { defineConfig } from 'seedcord';
// ---cut---
export default defineConfig({
    root: './src',
    instance: './bot.ts',
    build: { start: './index.ts' },
    dev: {
        hmr: { typecheck: true }
    }
});
```

`typecheck` starts switched off because it costs a second node process. With `typecheck: true`, `tsc` waits until your bot is ready, which keeps your first login quick.

`typecheck` also takes an object with a `tsconfig` path, for checking against a different tsconfig.

```ts twoslash title="seedcord.config.ts"
import { defineConfig } from 'seedcord';
// ---cut---
export default defineConfig({
    root: './src',
    instance: './bot.ts',
    build: { start: './index.ts' },
    dev: {
        hmr: {
            typecheck: { tsconfig: './tsconfig.build.json' }
        }
    }
});
```

The path resolves against `root`, like the other paths in `dev.hmr`.

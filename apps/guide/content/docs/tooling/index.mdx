A seedcord project has two config files, because two different programs read them. `seedcord dev`, `codegen`, `build`, and `commands deploy` have to import your bot before it runs, so they need its path from somewhere other than the bot itself. `seedcord.config.ts` holds that path for the CLI. The `new Seedcord({ ... })` call in `src/bot.ts` builds a [`Seedcord`](ref:gateway/Seedcord) bot and configures it while it runs.

The CLI looks for `seedcord.config.ts` or `seedcord.config.mts` in the directory you run it from.

```ts twoslash title="seedcord.config.ts"
import { defineConfig } from 'seedcord';

export default defineConfig({
    root: './src',
    instance: './bot.ts',
    build: { start: './index.ts' }
});
```

Only `instance` is required. `build.start` is optional. Without it, the build's `index.mjs` default-exports the bot for your own node server to start. An edge bot, which [runs on Cloudflare Workers](/build/workers), leaves it out too. [Your first bot](/first-bot#where-your-folders-resolve) explains how `root`, `instance`, and `build.start` fit together.

Every other key is optional: `root`, `files`, `vitePlugins`, `tunnel`, `hmr`, `idleAnimation`, the rest of `build`, and `port` on an edge bot. [The config reference](/build/config) lists each one with its default. `vitePlugins` takes a function that returns [Vite plugins](/build/vite-plugins), like `() => [yaml()]`.

## The commands

{/* prettier-ignore-start */}

| command | what it does |
| --- | --- |
| [`seedcord dev`](/tooling/dev) | runs your bot, reloads a changed file in place, and prints its logs in a terminal you can filter. An edge bot runs in workerd |
| [`seedcord codegen`](/tooling/codegen) | imports your bot and command files, then writes `seedcord-gen.d.ts` into `root` |
| [`seedcord build`](/build) | type checks your bot and bundles it for a server, a Cloudflare Worker, or another program to import |
| [`seedcord commands`](/tooling/commands) | deploys your commands to Discord, lists what Discord holds, and deletes the ones you no longer want |

{/* prettier-ignore-end */}

A project from `create-seedcord` wraps these as scripts, along with `check`, `commands:deploy`, and the `deploy` and `types` scripts of an edge bot. [Your first bot](/first-bot#scripts) lists every one.

## Your bot's config

`src/bot.ts` holds the second config, the one your bot reads. Every key gets taught on the page that needs it, inside a real `new Seedcord({ ... })` sample. The last column links to that page.

`bot`, `subscribers`, `bot.interactions`, and `bot.commands` are required. A gateway bot also has to set `bot.events` and `bot.clientOptions`. Every other key is optional.

{/* prettier-ignore-start */}

| key | what it sets | where it's taught |
| --- | --- | --- |
| `bot.interactions` | the folder seedcord scans for handlers, plus middleware and ignored ids | [Components](/components) |
| `bot.commands` | the folder seedcord scans for commands, and `guilds`, the test servers that bare `@RegisterCommand()` commands deploy to | [Commands](/commands), [Test servers](/commands/deployed#test-servers) |
| `bot.emojis` | the emoji names [`Emojis`](ref:gateway/Emojis) resolves at startup | [Components](/components) |
| `bot.events` | the folder seedcord scans for event handlers. Gateway only | [Events](/events) |
| `bot.clientOptions` | passed straight to the discord.js `Client`. Gateway only | [Your first bot](/first-bot) |
| `subscribers` | the folder seedcord scans for bus subscribers | [The bus](/events/bus) |
| `errors` | how a fault renders, what gets logged, which api error codes get ignored | [Tuning error behavior](/replying/error-behavior) |
| `notifications` | the contact name in the generic unknown-error message | [Faults](/replying/faults) |
| `botColor` | the accent on every [`BuilderComponent`](ref:core/BuilderComponent) you build | [Components](/components) |
| `ownerIds` | the ids [`OwnerOnly`](ref:core/OwnerOnly) treats as owners | [Gates](/checks/gates) |
| `store` | a durable store for framework state. The default keeps it in memory and loses it on restart | [The rate limiter](/checks/rate-limiter) |
| `logger` | the level, the sinks, and the per-channel overrides | [Configuring the logger](/tooling/logger-config) |
| `lifecycle` | `shutdownDeadline`, how long shutdown may take | [The lifecycle](/plugins/lifecycle) |

{/* prettier-ignore-end */}

<Callout type="transport">

Each transport package declares its own `Seedcord` and its own config type, and a few keys only exist on one of them.

- Both http configs take `bot.restOptions`. Only a node http server takes `port`, which defaults to 3000, and `port: false` lets [your own server](/build/embed) host the bot. TypeScript rejects `port`, `lifecycle`, and `healthCheck` on an edge bot.
- `healthCheck` takes different options on gateway and on a node http server. [The health server](/build/server#the-health-server) covers both.
- [`Emojis`](ref:gateway/Emojis) on gateway holds a subclass of [`ResolvedEmoji`](ref:core/ResolvedEmoji) tied to the discord.js `GuildEmoji` or `ApplicationEmoji`. [`Emojis`](ref:http/Emojis) on http holds a plain `ResolvedEmoji`.

</Callout>

The reference site has the full type of every one of these, down to each nested field.

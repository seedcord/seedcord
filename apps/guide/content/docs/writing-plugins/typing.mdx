---
title: Typing what you ship
description: Get your plugin's methods typed on this.core in every bot that attaches it, even though each bot's author picks the key.
---

You can't declare your plugin on [`Core`](ref:gateway/Core) yourself because the bot's author picks the key. Two things carry your types to the bot's handlers. [`attach`](ref:gateway/Seedcord.attach) returns the bot typed with your instance under the key, and [`seedcord codegen`](/tooling/codegen) copies that instance type onto `Core`. The [bot-side typing page](/plugins/typing) shows that step. The type of each member a handler can call comes from your class. The key and any type argument come from the bot that attaches it.

## Why the first parameter is CoreBase

Codegen adds every attached plugin to the transport's `Core`, and `attach` reads your constructor's parameters. A first parameter typed as that `Core` would pull your own plugin back into the types `attach` reads. So `attach` rejects any first parameter narrower than `CoreBase` at compile time.

```ts twoslash
// @errors: 2345
import { Plugin, Seedcord } from '@seedcord/gateway';

import type { Core } from '@seedcord/gateway';

declare const seedcord: Seedcord;

class Uptime extends Plugin {
    public constructor(host: Core) {
        super(host);
    }

    public async init(): Promise<void> {}
}

seedcord.attach('uptime', Uptime);
```

The compiler rejects `Uptime` as the argument to `attach` and prints this requirement under the call.

```txt output
this plugin constructor must take CoreBase as its first parameter and read the transport Core off this.core
```

Type the first parameter as [`CoreBase`](ref:core/CoreBase), the part of `Core` that every transport shares. To reach the transport's `Core`, read `this.core`, which your base class already types. [Writing a plugin](/writing-plugins#what-the-constructor-takes) has the working constructor.

## A plugin with a type parameter

A plugin that stores values for the bot, like a key-value cache, can't fix their type when you write it. A type parameter lets the bot choose.

```ts twoslash
import { Plugin, Seedcord } from '@seedcord/gateway';

declare const seedcord: Seedcord;

// ---cut---
interface Session {
    userId: string;
}

export class KeyValue<TValue> extends Plugin {
    private readonly entries = new Map<string, TValue>();

    public async init(): Promise<void> {}

    public get(key: string): TValue | undefined {
        return this.entries.get(key);
    }
}

const bot = seedcord.attach('sessions', KeyValue<Session>);
const session = bot.sessions.get('abc');
//    ^?
```

Writing `KeyValue<Session>` in the `attach` call sets `TValue`, so `session` comes back as `Session | undefined`. The `<Session>` after a value is an instantiation expression. A handler reading `this.core.sessions` gets the same type.

<Callout type="warning">

If you pass `KeyValue` alone, `TValue` becomes `unknown`, the fallback for a type parameter with no `extends`. That holds even when `TValue` has a default. Passing a value to the constructor doesn't set `TValue` either. Tell your users to write the type argument in the `attach` call.

</Callout>

### Taking the type from an option

A static `with()` on your class can take a type from the options that it's given. It takes the options and returns a class with them already set. `Flags` below takes a list of names, and its `isOn()` only accepts a name from that list.

With a type argument, the bot's author would write the list twice, once as a type and once as the value. `attach` can't infer the type from a value that you pass it.

```ts twoslash
import { Plugin, Seedcord } from '@seedcord/gateway';

import type { CoreBase } from '@seedcord/gateway';

declare const seedcord: Seedcord;

// ---cut---
export abstract class Flags<TName extends string> extends Plugin {
    protected abstract readonly names: readonly TName[];

    public static with<TName extends string>(
        names: readonly TName[]
    ): new (host: CoreBase) => Flags<TName> {
        const Attached = class extends Flags<TName> {
            protected readonly names = names;
        };
        Object.defineProperty(Attached, 'name', { value: 'Flags' });
        return Attached;
    }

    public async init(): Promise<void> {}

    public isOn(name: TName): boolean {
        return this.names.includes(name);
    }
}

const WithNames = Flags.with(['beta', 'dark']);
const { flags } = seedcord.attach('flags', WithNames);
//      ^?
```

`Flags.with(['beta', 'dark'])` is an ordinary generic call, so TypeScript infers `TName` from the array. `flags` comes back as `Flags<'beta' | 'dark'>`, and its `isOn()` only takes those two names.

`with()` returns a subclass because `attach` takes a class and builds the instance itself. `Attached` holds `names` as a class field.

`Flags` is `abstract`, which makes `attach('flags', Flags)` a compile error. Without that, a bot could attach the class directly and get the untyped version without noticing.

Two things are different from a plugin without `with()`:

- **Where the options go.** `attach` passes every argument after the class to your constructor, and that's where a plugin's options usually go. Your users pass them to `with()` here, so say that in your README.
- **The class name.** The class that `with()` returns has its own name, `Attached` in this sample, and seedcord's logger labels a plugin's lines with its class name. The `Object.defineProperty` line sets that name to `Flags`.

[`OAuth.with()`](ref:plugin-oauth/OAuth.with) in `@seedcord/plugin-oauth` works this way.

Skip `with()` when your options don't change a type. A plain constructor argument is less for your users to learn.

## Reading another plugin

A plugin on the base from `@seedcord/core/plugin` has a `this.core` typed as `CoreBase`, which doesn't list attached plugins. If you read another plugin by key there, it fails to compile.

```ts twoslash
// @errors: 2339
import { Plugin } from '@seedcord/core/plugin';

export class Greeter extends Plugin {
    public async init(): Promise<void> {
        this.core.hello.greet('world');
    }
}
```

A plugin on a transport base can't read another plugin by key either. Codegen writes the key into the bot's project, so it doesn't exist when your plugin's package builds. Take the other plugin as a constructor argument, which `attach` checks for you.

```ts twoslash
import { Plugin, Seedcord } from '@seedcord/gateway';

import type { CoreBase } from '@seedcord/gateway';

declare const seedcord: Seedcord;

class Hello extends Plugin {
    public async init(): Promise<void> {}

    public greet(name: string): string {
        return `hi, ${name}`;
    }
}

class Greeter extends Plugin {
    public constructor(
        host: CoreBase,
        private readonly hello: Hello
    ) {
        super(host);
    }

    public async init(): Promise<void> {
        this.logger.info(this.hello.greet('world'));
    }
}

const bot = seedcord.attach('hello', Hello);
bot.attach('greeter', Greeter, bot.hello);
```

`attach` returns the bot typed with the `hello` key, so `bot.hello` is the `Hello` instance that the `Greeter` constructor takes. The bot's author writes those last two lines. Tell your users to attach `Hello` first. If they attach `Greeter` first, `bot.hello` doesn't exist and the call fails to compile. Pass the other plugin when yours needs its methods. For a setting, pass the value itself.

If your plugin reads keys out of the bot's files, like tag names, [codegen can type them](/writing-plugins/codegen). A plugin can also [limit itself to one transport or runtime](/writing-plugins/runtimes).

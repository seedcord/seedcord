A status page or a dashboard for your bot needs a frontend, the HTML and scripts that a browser loads. It also needs routes that send the frontend the bot's data. Without a way to serve both from the bot, you'd host the frontend on its own site and run a second web server for a route or two.

Your bot serves both. Each Vite `index.html` in a `client/` folder beside `seedcord.config.ts` is a page, and a plugin answers the routes that the page fetches.

## A first page

Say you want a page that shows how long your bot has been running. It needs three files:

```txt plain
my-bot/
├── client/
│   └── uptime/
│       ├── index.html
│       └── main.ts
├── src/
│   ├── bot.ts
│   └── plugins/
│       └── Uptime.ts
└── seedcord.config.ts
```

`client/uptime/index.html` is the page at `/uptime/`. A `client/index.html` would be the page at `/`. The HTML is the same file that a Vite app starts from:

```html plain title="client/uptime/index.html"
<!doctype html>
<html lang="en">
    <head>
        <meta charset="utf-8" />
        <title>Uptime</title>
    </head>
    <body>
        <h1 id="uptime">Starting…</h1>
        <script type="module" src="./main.ts"></script>
    </body>
</html>
```

The `<script>` loads `./main.ts` from the page's own folder. That script asks the bot for `/api/uptime` and writes the answer into the heading:

```ts plain title="client/uptime/main.ts"
const response = await fetch('/api/uptime');
if (!response.ok)
    throw new Error(
        `/api/uptime answered ${String(response.status)}`
    );
const { seconds } = (await response.json()) as {
    seconds: number;
};

document.getElementById('uptime')!.textContent =
    `Up for ${String(seconds)}s`;
```

The page doesn't have the bot's data in it. The browser loads the page first, then your script fetches `/api/uptime`, and the plugin in the next section answers that route.

## Answering web requests

A plugin answers a request when you give it a [`fetch()`](ref:core/Plugin.fetch) method. It takes a web `Request` and returns a `Response`, or `undefined` to pass the request on.

```ts twoslash title="src/plugins/Uptime.ts"
import { Plugin } from '@seedcord/gateway';

const UPTIME = new URLPattern({ pathname: '/api/uptime' });

export class Uptime extends Plugin {
    private readonly startedAt = Date.now();

    public async init(): Promise<void> {}

    public override fetch(request: Request): Response | undefined {
        if (!UPTIME.test(request.url)) return undefined;
        const ms = Date.now() - this.startedAt;
        return Response.json({ seconds: Math.round(ms / 1000) });
    }
}
```

seedcord doesn't route requests for you, so you have to check the path in each plugin's `fetch()`. `Uptime` does that with a [`URLPattern`](https://developer.mozilla.org/en-US/docs/Web/API/URLPattern), which Node, Bun, and Workers all have built in. It answers `/api/uptime` and returns `undefined` for every other path, which passes the request on to the next step.

To put the route on your bot, attach `Uptime` in `bot.ts` with `attach('uptime', Uptime)` like [any other plugin](/plugins). This sample imports `Plugin` from `@seedcord/gateway`. On an http bot, the `Plugin` from `@seedcord/http` has the same `fetch()`.

You can also answer other requests in `fetch()`, like a webhook that GitHub posts, or return HTML that your plugin builds.

<Callout type="tip">

If the HTML itself has to change with each request, have your plugin's `fetch()` build it and return it. [Hot reload](/tooling/hot-reload#pages-in-your-browser) covers what `seedcord dev` adds to that HTML.

</Callout>

<Callout type="warning">

Anyone who can reach your bot can request `/api/uptime`, the same as the page does. Before a route returns something private, like a server's settings, check who's asking. The [OAuth plugin](/plugins/oauth) can check that for you by logging people in with Discord.

</Callout>

### Which step answers

seedcord tries these steps in order, and the first one to return a `Response` answers the request:

{/* prettier-ignore-start */}

| step | gateway | http |
| --- | --- | --- |
| 1 | the [health path](/build/server#the-health-check) | the health path, on a server |
| 2 | a built page or a file from `public/`, for a GET or HEAD | the same. On Workers, Cloudflare serves them before the bot runs |
| 3 | (none) | the interactions engine, for an interaction that Discord sent |
| 4 | each plugin's [`fetch()`](ref:core/Plugin.fetch), in attach order | each plugin's [`fetch()`](ref:core/Plugin.fetch), in attach order |
| 5 | a 404 | the interactions engine for a POST, a 404 for anything else |

{/* prettier-ignore-end */}

The bot answers with a built page or a `public/` file before any plugin runs, so keep your routes off those paths.

On an http bot, the interactions engine runs your command and component handlers. It answers every interaction from Discord before your plugins run, whatever path your interactions endpoint URL uses. That way a slow `fetch()` never uses up Discord's three seconds. Discord's [webhook events](https://discord.com/developers/docs/events/webhook-events) aren't interactions, so they reach your `fetch()` like any other request.

### Check the path before you await

Your `fetch()` runs for every request that gets past the plugins attached before it, and the plugins after yours wait until it returns. Check the path and the method, return `undefined` for anything that isn't yours, and only then await anything, like reading the body or querying a database.

```ts twoslash title="src/plugins/GithubHooks.ts"
import { Plugin } from '@seedcord/http';
// ---cut---
const PUSH = new URLPattern({ pathname: '/github/:repo/push' });

export class GithubHooks extends Plugin {
    public async init(): Promise<void> {}

    public override async fetch(
        request: Request
    ): Promise<Response | undefined> {
        if (request.method !== 'POST') return undefined;
        const repo = PUSH.exec(request.url)?.pathname.groups.repo;
        if (!repo) return undefined;

        const body = await request.text();
        this.logger.info(`push to ${repo}, ${body.length} bytes`);
        return new Response(null, { status: 204 });
    }
}
```

`:repo` in the pattern matches one part of the path, and `exec()` returns it under `pathname.groups`. Both checks return before the `await`, so a request for any other route never waits on the body.

Anyone can post to a public route, so check the request's `X-Hub-Signature-256` header against `body` before you trust it. Read the body with `text()` for that check because [GitHub signs the exact payload](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) that it sends, and `json()` would hand you the parsed object without those bytes. If a push can be bigger than 1 MiB, raise `server.bodyLimit` because the [web server](/build/server#the-web-server) answers a larger body with a 413 before any plugin runs.

### Reading the body

<Callout type="warning">

A request's body can only be read once. If you read it in `fetch()`, or call `getReader()` on it, and then return `undefined`, the plugins after yours can't read it. That request fails with a 500, and seedcord logs this error. In that error, `hooks` is the plugin's attach key:

```txt output
[1241] GithubHooks at hooks read or locked the body of a request to /github/seedcord/push without answering it. The steps after it can't read that body again. Check the path in fetch before you touch the body.
```

</Callout>

`GithubHooks` avoids that by reading the body only after both checks pass. If you need the body to decide whether to answer, read a copy with `await request.clone().text()` after your path check.

### When `fetch()` throws

seedcord logs the error with the method and the path on your plugin's logger and answers the request with a 500. The plugins after yours never get that request.

### Linking to your route

Sometimes your plugin has to tell someone where one of its routes is, like the webhook URL that you paste into GitHub. For that, it needs the address people reach the bot at. Read it from [`core.url`](ref:core/CoreBase.url):

```ts twoslash title="src/plugins/GithubHooks.ts"
import { Plugin } from '@seedcord/http';
// ---cut---
export class GithubHooks extends Plugin {
    public async init(): Promise<void> {
        const url = new URL('github/seedcord/push', this.core.url);
        this.logger.info(`add this webhook in GitHub: ${url.href}`);
    }
}
```

A path that starts with a slash replaces the whole path of `core.url`, so write your route's path without one. For a bot at `https://example.com/bot`, `new URL()` keeps the `/bot` part for `'github/seedcord/push'` and removes it for `'/github/seedcord/push'`.

`core.url` comes from [`server.url`](/build/server#your-bots-address), which the bot's author has to set. If they haven't, `core.url` throws an error with the line to add, so read it in `init()` to make the error stop the bot at startup. Under `seedcord dev`, `core.url` is the bot's localhost or tunnel address.

### Where requests arrive

A bot on Node or Bun serves web requests on its [web server](/build/server#the-web-server), which listens on port 3000 unless the bot sets `server.port`. If you [embed the bot in your own server](/build/embed), it gets only the paths that you pass to `bot.fetch()`.

Set up whatever your `fetch()` reads in `init()` because every `init()` finishes before the first request reaches `fetch()`. A `ready()` can still be running when a request arrives, and so can an `init()` that you moved to the Ready phase. [The lifecycle page](/plugins/lifecycle#where-each-one-runs) has the full order.

<Callout type="transport" only="edge">

Once a plugin has `fetch()`, the first request that reaches the Worker starts the bot so the plugin can answer it. Cloudflare runs your Worker in isolates, and each one runs its own copy of the bot. A crawler's request starts the bot too. Without a plugin that has `fetch()`, the Worker answers anything besides a POST with a 404 before the bot starts.

</Callout>

## Live updates

Say a page shows how many times `/ping` has run. Without a way for the bot to send the new count, the page would fetch `/api/pings` every second and get the same answer most of the time. [Server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events) let the bot send it instead. The browser opens one request. Your plugin has to keep it open and write a line to it each time the count changes.

```ts twoslash title="src/plugins/PingCounter.ts"
import { Plugin, ShutdownPhase } from '@seedcord/gateway';
import type { CoreBase } from '@seedcord/gateway';

const PINGS = new URLPattern({ pathname: '/api/pings' });
const encoder = new TextEncoder();

type Tab = ReadableStreamDefaultController<Uint8Array>;

export class PingCounter extends Plugin {
    private runs = 0;
    private readonly tabs = new Set<Tab>();

    public constructor(host: CoreBase) {
        super(host, { dispose: { phase: ShutdownPhase.Unbind } });
    }

    public async init(): Promise<void> {}

    public bump(): void {
        this.runs++;
        for (const tab of this.tabs) this.send(tab);
    }

    public override fetch(request: Request): Response | undefined {
        if (request.method !== 'GET' || !PINGS.test(request.url))
            return undefined;
        let tab: Tab;
        const events = new ReadableStream<Uint8Array>({
            start: (controller) => {
                tab = controller;
                this.tabs.add(tab);
                this.send(tab);
            },
            cancel: () => void this.tabs.delete(tab)
        });
        return new Response(events, {
            headers: {
                'content-type': 'text/event-stream',
                'cache-control': 'no-cache'
            }
        });
    }

    public override dispose(): void {
        for (const tab of this.tabs) tab.close();
        this.tabs.clear();
    }

    private send(tab: Tab): void {
        const line = `data: ${String(this.runs)}\n\n`;
        tab.enqueue(encoder.encode(line));
    }
}
```

Every browser tab on the page opens its own stream, so `PingCounter` has to keep one entry per tab in `tabs` to reach them all. `start` sends the current count right away, and `cancel` runs when the tab closes. A message is a `data:` line and a blank line after it, which is why `send()` ends with two newlines. With `no-cache`, a cache between the bot and the browser asks the bot again each time. That way a tab never gets an old copy of the stream.

Attach it with `attach('pings', PingCounter)`. To send every open tab the new count, call `this.core.pings.bump()` in your `/ping` handler.

On the page, the browser's [`EventSource`](https://developer.mozilla.org/en-US/docs/Web/API/EventSource) reads those messages:

```ts plain title="client/pings/main.ts"
const events = new EventSource('/api/pings');
events.addEventListener('message', ({ data }) => {
    document.getElementById('pings')!.textContent =
        `/ping ran ${data} times`;
});
```

`EventSource` [connects again by itself](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events) after the stream closes. Both a restart and a plugin reload close the stream. Under `seedcord dev`, a plugin reloads when you save its file. Your [`dispose()`](ref:core/Plugin.dispose) on the old plugin closes its streams, and the next connection reaches the new plugin.

With `dispose: { phase: ShutdownPhase.Unbind }` in the constructor, `dispose()` runs in [`ShutdownPhase.Unbind`](ref:core/ShutdownPhase), the phase where the web server stops. The server waits for every open connection before it stops. In the default phase, `dispose()` runs after that wait, so each open tab would hold the shutdown until the wait timed out.

<Callout type="transport" only="edge">

On Workers, your `/ping` handler can't write to the page's stream. It runs in one request, and the page's stream belongs to another. [Cloudflare stops a request](https://developers.cloudflare.com/workers/observability/errors/) from writing to a stream that a different request opened. Each isolate also keeps its own count. Have the page fetch `/api/pings` on a timer, and answer it with the count:

```ts plain
public override fetch(request: Request): Response | undefined {
    if (request.method !== 'GET' || !PINGS.test(request.url)) return undefined;
    return Response.json({ runs: this.runs });
}
```

</Callout>

## React or another framework

To use React, Vue, or another framework that renders in the browser, add its Vite plugin to [`vitePlugins`](/build/vite-plugins) in `seedcord.config.ts`. For React, that's `@vitejs/plugin-react`:

<Shell add="react react-dom" />

<Shell add="-D @vitejs/plugin-react @types/react @types/react-dom" />

```ts plain title="seedcord.config.ts"
import react from '@vitejs/plugin-react';
import { defineConfig } from 'seedcord';

export default defineConfig({
    root: './src',
    instance: './bot.ts',
    build: { start: './index.ts' },
    vitePlugins: () => [react()]
});
```

With `react()` in the list, saving a component under `seedcord dev` updates it in the open tab without a reload.

<Callout type="tip">

You can add any other Vite plugin for browser code to the same list, like `@tailwindcss/vite` for Tailwind. The plugins in `vitePlugins` run on your pages and on your bot's code, under `seedcord dev` and in a build. seedcord serves your pages from `/`, so it stops with `CliViteBaseUnsupported` if a plugin sets Vite's `base`.

</Callout>

### Types for the browser code

Your bot's tsconfig only includes `src/`, so `tsc` never checks the files in `client/`. The bot's tsconfig also doesn't have the browser's types, like `document`. Give the folder its own tsconfig:

```json plain title="client/tsconfig.json"
{
    "extends": "@seedcord/tsconfig",
    "compilerOptions": {
        "rootDir": "./",
        "jsx": "react-jsx",
        "lib": ["ESNext", "DOM", "DOM.Iterable"],
        "types": ["vite/client"]
    },
    "include": ["**/*.ts", "**/*.tsx"]
}
```

`"DOM"` in `lib` types `document`, and `vite/client` types imports that Vite handles, like a `.css` file. Run `tsc --noEmit -p client` as well as your bot's own type check. Only `client/` gets the DOM types, so `document` in your bot's code is still an error.

## Under seedcord dev

`seedcord dev` serves your pages on the same address as your bot, through Vite. If you save a file that a page imports, the open tab updates. If you save your bot's code, every open tab reloads once the bot has loaded the change, so the page shows the new data. [Hot reload](/tooling/hot-reload) lists which of your bot's files need a restart.

If you add your first page while `seedcord dev` runs, the terminal shows the **Restart required** card. Press `r` to restart the bot and serve the page.

<Callout type="warning">

In dev, a browser can load any file in `client/` except the `.html` files, which go to your bot. The pages are the one exception. A build only writes the pages and the files that they import. If a page links `/logo.png` by its full path, dev serves `client/logo.png`, but the build doesn't copy it, so your bot answers that path with a 404. Put files like that, and your favicon, in [`public/`](#the-public-folder).

</Callout>

## After a build

`seedcord build` bundles each page with the scripts and styles it imports. Vite writes those under `/assets/` with a hash of their contents in each file name.

<Tabs>
<Tab label="Node and Bun">

The build writes the pages to `client/` inside your `outDir`, and the bot serves them from its [web server](/build/server#the-web-server) before any plugin route. The bot redirects a request for `/uptime` or `/uptime/index.html` to `/uptime/` with a 307. The bot sends files under `/assets/` with a header that lets browsers cache them for a year. A new build gives a changed file a new name, so a visitor never keeps an old one.

The build also writes each module under `root` to the same path in `outDir`. If `root` has a `client/` folder of bot code, building your pages would delete those modules, so seedcord stops with `CliBuildClientFolderTaken`.

</Tab>
<Tab label="Workers">

The build writes the pages as Cloudflare's [static assets](https://developers.cloudflare.com/workers/static-assets/), which Cloudflare serves before your Worker runs. seedcord writes a `_headers` file with a one-year cache rule for the files under `/assets/`. If you put your own `_headers` file in `public/`, seedcord keeps yours and doesn't write one, so copy the one-year rule for `/assets/*` into it.

</Tab>
</Tabs>

<Callout type="transport" only="edge">

Cloudflare [checks for a matching asset](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/) before it runs your Worker. If you have a page at `/`, like `client/index.html`, Cloudflare answers a POST to `/` with a 405 itself, and Discord's interactions never reach your bot. Set your bot's Interactions Endpoint URL in the Developer Portal to a path like `/interactions` on your bot's address. `seedcord dev` sets its own path, so only your deployed bot needs this.

</Callout>

## The public folder

Put a file that a browser asks for by name, like `robots.txt` or a favicon, in a `public/` folder beside `seedcord.config.ts`. The bot serves those files unchanged at the same path, so `public/robots.txt` is the file at `/robots.txt`. A bot on Node or Bun serves `public/` once it has a page, and a bot on Workers always deploys it.

Keep your own files out of `public/assets/`, and don't put a page in `client/assets/`. seedcord sends everything under `/assets/` with a one-year cache header, so visitors would keep an old copy of a file you replace there. If you have a page and break either rule, seedcord stops with `CliAssetsPathTaken`.

## Another folder for your pages

Set `client.dir` in `seedcord.config.ts` to serve your pages from another folder. The path is relative to the folder that holds the config, the same as `emojis.dir`.

```ts twoslash title="seedcord.config.ts"
import { defineConfig } from 'seedcord';

export default defineConfig({
    root: './src',
    instance: './bot.ts',
    build: { start: './index.ts' },
    client: { dir: './web' }
});
```

Keep `./web` inside the folder that holds `seedcord.config.ts`. Keep `root` (`./src` here) out of `./web` too because a browser can load every file in `./web`. If you break either rule, seedcord stops with `CliClientDirUnusable`. The build still writes the pages to `client/` inside your `outDir`.

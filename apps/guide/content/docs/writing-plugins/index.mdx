title: Writing a plugin
description: Add your own functionality to seedcord with a plugin, a class that starts and stops with your bot and that every handler reads from this.core.
---

Say your bot talks to an outside service, like a metrics API or a cache, and exports its client from `bot.ts`. Without a plugin, nothing closes that client when the bot shuts down, and a handler can import it before it has connected. As a plugin, the client starts and stops with your bot, and handlers read it from [`this.core`](ref:core/CoreBase) under the key you attach it with. If nothing needs to start or stop with the bot, a plain module works too.

To write a plugin, extend [`Plugin`](ref:core/Plugin) and write [`init()`](ref:core/Plugin.init). Everything else on `Plugin` is optional. The samples on this page import from `@seedcord/gateway`, and an http bot imports the same names from `@seedcord/http`.

```ts twoslash title="src/plugins/Uptime.ts"
import { Plugin } from '@seedcord/gateway';

export class Uptime extends Plugin {
    private startedAt = 0;

    public override async init(): Promise<void> {
        this.startedAt = Date.now();
    }

    public elapsed(): number {
        return Date.now() - this.startedAt;
    }
}
```

A new project has a plugin like this in `src/plugins/Uptime.ts`. `Uptime` doesn't declare a constructor, so you [`attach`](ref:gateway/Seedcord.attach) it with a key and the class.

```ts twoslash
import { Plugin, Seedcord } from '@seedcord/gateway';

declare const seedcord: Seedcord;

class Uptime extends Plugin {}

// ---cut---
export default seedcord.attach('uptime', Uptime);
```

## Calling it from a handler

A handler doesn't import the plugin from `bot.ts`. It reads `this.core.uptime`, where `uptime` is the key from the `attach` call.

```ts twoslash title="src/handlers/UptimeCommand.ts"
import { SlashHandler, SlashRoute } from '@seedcord/gateway';
// ---cut-start---
import { Plugin } from '@seedcord/gateway';

class Uptime extends Plugin {
    private startedAt = 0;

    public override async init(): Promise<void> {
        this.startedAt = Date.now();
    }

    public elapsed(): number {
        return Date.now() - this.startedAt;
    }
}

declare module '@seedcord/gateway' {
    interface Core {
        uptime: Uptime;
    }
}
// ---cut-end---

@SlashRoute('uptime')
export class UptimeCommand extends SlashHandler<'uptime'> {
    public async execute(): Promise<void> {
        const ms = this.core.uptime.elapsed();
        //    ^?
        await this.reply(
            `Up for ${Math.floor(ms / 1000)} seconds.`
        );
    }
}
```

To type `this.core.uptime`, run [`seedcord codegen`](/tooling/codegen) after you attach the plugin. The [typing page](/writing-plugins/typing) explains how the return type of `elapsed()` reaches it.

A handler can use every public member of your class except the ones that only seedcord uses: `init()`, [`ready()`](ref:core/Plugin.ready), [`dispose()`](ref:core/Plugin.dispose), [`codegen()`](ref:core/Plugin.codegen), [`onHmr()`](ref:core/Plugin.onHmr), [`dispatchMembers`](ref:core/Plugin.dispatchMembers), [`prepareCommands()`](ref:core/Plugin.prepareCommands) and [`fetch()`](ref:core/Plugin.fetch). `startedAt` in the first sample is private, so a handler reads the time through `elapsed()`. TypeScript rejects a handler that writes to `startedAt`. Keep connections and state private, and make public only the methods you want handlers to call.

Put work in `ready()` when it needs the logged-in client or the bot's application id. Neither is ready yet when `init()` runs. Handlers start receiving interactions when the last startup phase, Ready, begins. `ready()` runs in that phase too, so a handler can call your method before `ready()` finishes. If a method reads something that `ready()` sets, check for it first. Throw if the handler can't do its job without it, and return early if it can skip the work. The full startup order is on [the lifecycle page](/plugins/lifecycle).

<Callout type="transport">

On Cloudflare Workers, the first request waits for the whole startup, `ready()` included, so a handler there never runs before `ready()` finishes.

</Callout>

## Adding a value to every handler

Suppose your plugin stores settings for each guild, like how many warnings a member gets, and a handler needs the settings of the guild it runs in. Without `dispatchMembers`, every handler would read the guild id from its interaction and pass it into every call. A function in your plugin's [`dispatchMembers`](ref:core/Plugin.dispatchMembers) looks up the settings once per interaction, so a handler reads `this.settings` without passing anything.

```ts twoslash title="src/plugins/GuildSettings.ts"
import { Plugin } from '@seedcord/gateway';

import type { DispatchOrigin } from '@seedcord/gateway';

interface Settings {
    logChannel: string | null;
    maxWarnings: number;
}

const DEFAULTS: Settings = { logChannel: null, maxWarnings: 3 };

export class GuildSettings extends Plugin {
    private readonly byGuild = new Map<string, Settings>();

    public override readonly dispatchMembers = {
        settings: ({ guildId }: DispatchOrigin): Settings => {
            if (!guildId) return DEFAULTS;
            return this.byGuild.get(guildId) ?? DEFAULTS;
        }
    };
}
```

`dispatchMembers` is a plain object of functions. seedcord calls each function once per interaction, and once per event if the event has a handler. Each handler gets what `settings` returns as `this.settings`. If a function is async, handlers get the value it resolves to.

Each function gets a [`DispatchOrigin`](ref:core/DispatchOrigin), with these fields:

```ts twoslash
// @noErrors
import type { DispatchOrigin } from '@seedcord/gateway';

declare const origin: DispatchOrigin;
// ---cut---
origin.
//     ^|
```

Every field can be null:

- `guildId` and `guildLocale` are null outside a guild.
- `channelId` is null when the interaction or event doesn't happen in a channel.
- `userId` is null on an event without a user, and `userLocale` is null on every gateway event. An interaction always has both.

For that reason, `settings` returns the defaults when `guildId` is null.

To type `this.settings` on every handler, attach the plugin and run [`seedcord codegen`](/plugins/typing). Codegen writes one line for each key into `seedcord-gen.ts`, and TypeScript reads that line's type from the function's return type. Leave the `dispatchMembers` object without a type annotation. With one, like a `Record` of functions, `this.settings` becomes `unknown`.

```ts twoslash title="src/handlers/LimitsCommand.ts"
// ---cut-start---
import { SlashHandler, SlashRoute } from '@seedcord/gateway';

interface Settings {
    logChannel: string | null;
    maxWarnings: number;
}

declare module '@seedcord/gateway' {
    interface DispatchMemberValues {
        settings: Settings;
    }
    interface SlashRegistry {
        limits: { options: {}; cache: 'cached' };
    }
}
// ---cut-end---
@SlashRoute('limits')
export class LimitsCommand extends SlashHandler<'limits'> {
    public async execute(): Promise<void> {
        const { maxWarnings } = this.settings;
        //                           ^?
        await this.reply(`Members get ${maxWarnings} warnings.`);
    }
}
```

`maxWarnings` is a `number` because the `settings` function returns `Settings`. In [middleware](/checks/middleware) you read `this.settings` too, and in [gates](/checks/gates) and a [`Notice`](ref:core/Notice)'s `render` you read `ctx.settings`.

seedcord runs every plugin's `dispatchMembers` functions at the same time, and the handler waits until they've all returned or one has thrown. They run before middleware and gates, even for an interaction that a gate then refuses. So a slow function spends part of the [three seconds](/replying) that Discord gives a bot to answer an interaction. They also run for [autocomplete](/commands/autocomplete), which Discord sends as the user types. If only a few handlers need a value, give your plugin a method and call it through `this.core` in those handlers.

If a function throws, seedcord skips the middleware and handlers for that interaction or event, and logs and publishes the error with the code `CorePluginMemberThrew`. seedcord answers a command, a component, a context menu or a modal with the built-in [`Fault`](ref:core/Fault) card. It skips your bot's `defaultError` here because a card of your own might read the value that just failed. An autocomplete gets an empty list of choices. An event isn't answered at all.

Each key has to be free on every handler, so these fail:

{/* prettier-ignore-start */}

| if | fails at | code |
| --- | --- | --- |
| a key is a name that seedcord uses, like `reply`, `user` or `logger`, or a built-in object name like `constructor` | `attach()` | `CorePluginMemberReserved` |
| another plugin already uses the key | `attach()` | `CoreDuplicateName` |
| you attach a plugin that has `dispatchMembers` twice, since both copies add the same keys | `attach()` | `CorePluginAttachedTwice` |
| a handler or middleware defines a method or getter with the key | startup | `CoreDuplicateName` |
| a handler or middleware sets a field with the key, which would replace your value | every dispatch to it | `CoreDuplicateName` |

{/* prettier-ignore-end */}

<Callout type="transport">

Only a gateway bot receives events, so on an http bot the functions run once per interaction.

</Callout>

## Closing what init() opened

Without `dispose()`, a timer that `init()` starts keeps calling its callback after the bot begins shutting down. `seedcord dev` restarts your bot in the same process, so the timer from the last run still calls its callback, and any connection `init()` opened is still open. [`dispose()`](ref:core/Plugin.dispose) runs at shutdown, and it's where you close whatever `init()` started.

```ts twoslash title="src/plugins/Heartbeat.ts"
import { Plugin } from '@seedcord/gateway';
// ---cut---
export class Heartbeat extends Plugin {
    private timer: NodeJS.Timeout | undefined;

    public override async init(): Promise<void> {
        this.timer = setInterval(() => {
            this.logger.debug('still running');
        }, 30_000);
    }

    public override async dispose(): Promise<void> {
        clearInterval(this.timer);
    }
}
```

<Callout type="warning">

If `init()` throws, seedcord skips `dispose()`. If a plugin opens two things in `init()` and the second one fails, `init()` has to close the first itself.

</Callout>

The lifecycle page lists what seedcord cleans up [when `init()` fails](/plugins/lifecycle#when-init-fails). On Cloudflare Workers the shutdown phases never run, so `dispose()` runs only if your `init()` resolved and a later startup step failed. Write state as soon as it changes. The lifecycle page also lists the [other differences on Workers](/plugins/lifecycle#on-cloudflare-workers).

## Which base to import

Each transport exports its own `Plugin` class. A transport is how the bot talks to Discord, either the gateway websocket or http interactions. The base you extend sets the type of `this.core`.

{/* prettier-ignore-start */}

| import from | `this.core` has | extend it when your plugin |
| --- | --- | --- |
| `@seedcord/gateway` | the gateway [`Core`](ref:gateway/Core), which adds [`bot`](ref:gateway/Core.bot), [`startup`](ref:gateway/Core.startup) and [`shutdown`](ref:gateway/Core.shutdown) | reads [`bot`](ref:gateway/Core.bot), [`startup`](ref:gateway/Core.startup) or [`shutdown`](ref:gateway/Core.shutdown) |
| `@seedcord/http` | the http [`Core`](ref:http/Core), which adds [`startup`](ref:http/Core.startup) and [`shutdown`](ref:http/Core.shutdown) | reads [`startup`](ref:http/Core.startup) or [`shutdown`](ref:http/Core.shutdown) on an http bot (on Workers, [`shutdown`](/plugins/lifecycle#on-cloudflare-workers) throws) |
| `@seedcord/core/plugin` | [`CoreBase`](ref:core/CoreBase), the members both transports share, like [`config`](ref:core/CoreBase.config), [`rest`](ref:core/CoreBase.rest) and [`bus`](ref:core/CoreBase.bus) | only uses what both transports share |

{/* prettier-ignore-end */}

<Callout type="transport">

`config` follows the base you extend. The gateway base types it as [`GatewayConfig`](ref:gateway/GatewayConfig), the http base as [`HttpConfig`](ref:http/HttpConfig), and `CoreBase` as the shared [`Config`](ref:types/Config).

</Callout>

The base also sets which bots can attach the plugin: gateway bots for the gateway base, http bots for the http base, and bots on either transport for `@seedcord/core/plugin`. The gateway base also runs only on a server, while the http base and `@seedcord/core/plugin` run on Workers too. A plugin [can narrow that](/writing-plugins/runtimes).

To let bots on either transport attach a plugin you publish, extend `@seedcord/core/plugin` unless your plugin needs `bot`, `startup`, or `shutdown`. If you write a plugin only for your own bot, extend your bot's transport base or `@seedcord/core/plugin`.

## What the constructor takes

A plugin often needs options, like a connection string or a label. The constructor's first parameter is the host, the bot that seedcord passes in when you call `attach`. Type it as `CoreBase` and pass it to `super`. You define every parameter after it. You pass their values to `attach` after the plugin class, and TypeScript checks their types. If you type the first parameter as a transport's `Core`, the `attach` call fails to compile, and the [typing page](/writing-plugins/typing#why-the-first-parameter-is-corebase) gives the reason.

```ts twoslash
import { Plugin } from '@seedcord/gateway';

import type { CoreBase } from '@seedcord/gateway';

export class Uptime extends Plugin {
    public constructor(
        host: CoreBase,
        private readonly label: string
    ) {
        super(host);
    }

    public override async init(): Promise<void> {
        this.logger.info(`tracking ${this.label}`);
    }
}
```

`Uptime` takes `label` as its second parameter, so you write [`attach('uptime', Uptime, label)`](ref:gateway/Seedcord.attach).

Import `CoreBase` from the package you import `Plugin` from. On the `@seedcord/core/plugin` base, that's `@seedcord/core`, which a new bot doesn't install. Add it to your bot, and list it as a peer dependency when you publish the plugin, so the bot and the plugin share one copy. With two copies, `attach` rejects the plugin with the code `CorePluginFromOtherCore`. The `peerDependencies` entry is in [Publishing](/writing-plugins/publishing#the-peer-entry).

The second argument to `super()` is an optional [`PluginLifecycleSpec`](ref:core/PluginLifecycleSpec), and every field in it is optional too. `init` can take a [`StartupPhase`](ref:core/StartupPhase), and `dispose` can take any [`ShutdownPhase`](ref:core/ShutdownPhase) except `Release`. Both also take a `timeout` in milliseconds, and `ready` takes only a `timeout`. A timeout has to be a finite number above 0. Without them, `init()` runs in the Configuration phase, `dispose()` runs in the Disconnect phase, and the timeouts are 15000ms for `init()` and `ready()` and 10000ms for `dispose()`. A plugin that [declares a `transport` or a `runtime`](/writing-plugins/runtimes) has to pass the spec. [The lifecycle page](/plugins/lifecycle#moving-a-method-to-another-phase) has a sample.

<Callout type="warning">

The constructor runs whenever something loads `bot.ts`. [`seedcord codegen`](/tooling/codegen#codegen-constructs-your-bot) and `seedcord build` both load it, so a connection opened there opens on every codegen run and every build, even though no bot is running. In the constructor, only store the arguments. Open connections and read files in `init()`.

</Callout>

### Rejecting bad options

Catch a bad option, like an empty label, while the bot starts before anything connects. Call [`rejectOptions`](ref:core/Plugin.rejectOptions) from the constructor to stop the bot at the `attach` call.

```ts twoslash
import { Plugin } from '@seedcord/gateway';

import type { CoreBase } from '@seedcord/gateway';

// ---cut---
export class Uptime extends Plugin {
    public constructor(host: CoreBase, label: string) {
        super(host);

        if (label.length === 0)
            this.rejectOptions('label is empty');
    }
}
```

`rejectOptions` throws an error with the code `PluginOptionsRejected`, and its message starts with your plugin's class name, which a plain `throw` would leave out. The bot stops with this message.

```txt output
Uptime rejected its options. Label is empty.
```

## Logging

Log through [`this.logger`](ref:core/Plugin.logger). It exists from the constructor onward and labels each line with your class name. The logger writes each line to a channel, a named stream that a bot can filter or silence. `attach` sets the channel to the key before your constructor runs, so a plugin attached as `metrics` writes every line to the `metrics` channel. [The log channel section](/plugins#the-key-is-also-a-log-channel) shows how a bot filters it.

To label one job's lines, call [`this.logger.withLabel('sync')`](ref:logger/Logger.withLabel), which returns a logger with that label on the same channel. [`withChannel()`](ref:logger/Logger.withChannel) returns one that writes to another channel.

## Keeping records

A plugin that tracks posted messages or how far a sync got needs to read those records again after a restart. [`this.kv`](ref:core/Plugin.kv) is a key-value store for your plugin. It stores records in the bot's [kv driver](/built-ins/drivers), under your plugin's key. The bot's own [`core.kv`](ref:core/CoreBase.kv) and every other plugin write under their own prefixes, so the records don't mix. Records are stored as JSON, which is why the sample below types `postedAt` as a string. [Built-ins](/built-ins/) has the other collection methods and what JSON keeps.

```ts twoslash
import { Plugin } from '@seedcord/gateway';
// ---cut---
interface Post {
    channelId: string;
    postedAt: string;
}

export class Starboard extends Plugin {
    private readonly posts = this.kv.collection<Post>('post');
    private readonly tracked = new Map<string, Post>();

    public override async ready(): Promise<void> {
        for await (const [id, post] of this.posts.entries()) {
            this.track(id, post);
        }
    }

    public async add(id: string, post: Post): Promise<void> {
        await this.posts.set(id, post);
        this.track(id, post);
    }

    private track(id: string, post: Post): void {
        this.tracked.set(id, post);
        this.logger.debug(`${id} posted at ${post.postedAt}`);
    }
}
```

`add` saves a post before it tracks it, so a crash between the two still leaves the post for `ready()` to find after a restart. The restore runs in `ready()` after the bot has started. By then, a real `track()` can fetch the starred message from Discord.

Handlers can call `add()` while `ready()` is still restoring, so the same id can reach `track()` twice. Keep `track()` safe to call twice for one id, like the `Map` here, which replaces the first entry. A large collection can also take longer to restore than the 15 seconds `ready()` gets by default, and some drivers can't list their records at all. [Drivers](/built-ins/drivers) lists which ones.

`posts` reads `this.kv` in a field initializer. That works because `attach` sets it before your constructor runs, so the constructor and every method can read it too. Each attach key keeps its own records:

- If a bot attaches `Starboard` twice under two keys, each one keeps its own posts.
- If the bot renames the key, the plugin starts empty. The driver still holds the records under the old key.

The default driver keeps records in memory, so a restart loses them. To keep them, set `kv` in your bot's config to a driver that writes somewhere else. [Drivers](/built-ins/drivers) has a sample for each backend.

If you build a plugin with `new`, as in a test, it never gets a key, and `this.kv` throws `CorePluginKvOutsideAttach` if you read it.

---

npm search matches package names and keywords. Call your package `seedcord-plugin-<thing>`, like `seedcord-plugin-uptime`, and add `seedcord` and `plugin` to your keywords. Official plugins are named `@seedcord/plugin-<thing>`, and only seedcord can publish under `@seedcord`.

## The peer entry

Put whichever package you import [`Plugin`](ref:core/Plugin) from in `peerDependencies`, with the versions you tested against. Your plugin then uses the bot's copy. Below 1.0, a breaking change can ship in a minor, so the range tells people which versions work before they install. Keep the same package in `devDependencies` for your own builds.

The entry also controls how the `seedcord` CLI loads your plugin. `seedcord dev`, `build`, and `codegen` run the bot [through Vite](/build), which evaluates the bot's `@seedcord/*` packages itself. They read each installed package's `dependencies` and `peerDependencies`, and load one that lists a `@seedcord/*` package through Vite too. If a package doesn't list one, Node loads it. A plugin in such a package attaches fine from a plain Node script but fails under `seedcord codegen` with `CorePluginFromOtherCore`. Node and Vite each hold an instance of `@seedcord/core`, even though only one copy is installed. The CLI doesn't read `devDependencies` for this.

## A minimal package

This package holds a plugin on the `@seedcord/core/plugin` base that reads files through [`readFiles`](ref:utils/readFiles), so you list `@seedcord/core` as a peer and `@seedcord/utils` as a dependency. A second copy of `@seedcord/utils` still finds the bot's files, which is why the official plugins list it under `dependencies` too. For a plugin on the gateway or http base, list only that transport as a peer. The gateway one also needs `discord.js` in `devDependencies` because `@seedcord/gateway` peers on it.

```json title="package.json"
{
    "name": "seedcord-plugin-tags",
    "version": "0.1.0",
    "type": "module",
    "keywords": ["seedcord", "plugin"],
    "exports": {
        ".": {
            "types": "./dist/index.d.mts",
            "default": "./dist/index.mjs"
        }
    },
    "files": ["dist"],
    "scripts": {
        "build": "tsdown src/index.ts --format esm --dts"
    },
    "peerDependencies": {
        "@seedcord/core": "^0.14.0"
    },
    "dependencies": {
        "@seedcord/utils": "^0.10.0"
    },
    "devDependencies": {
        "@discordjs/builders": "^1.15.0",
        "@seedcord/core": "0.14.0",
        "@types/node": "^24",
        "envapt": "^9.2.0",
        "tsdown": "^0.23.7",
        "typescript": "^6.0.3"
    }
}
```

In `exports`, list `types` first, pointing at the declaration file that `tsdown` writes next to `index.mjs`. A bot reads your plugin's types from that file, and the [typing page](/writing-plugins/typing) explains what reaches the bot's `Core`. `files` limits the tarball to `dist` plus `package.json`. `@discordjs/builders` and `envapt` are there because `@seedcord/core` peers on them.

```json title="tsconfig.json"
{
    "compilerOptions": {
        "strict": true,
        "module": "esnext",
        "moduleResolution": "bundler",
        "target": "ES2024",
        "lib": ["ESNext"],
        "types": ["node"],
        "skipLibCheck": true,
        "noEmit": true
    },
    "include": ["src"]
}
```

`moduleResolution: "bundler"` lets TypeScript follow the `exports` maps of the `@seedcord` packages. `noEmit` is there because `tsdown` writes the output. Add `experimentalDecorators` only if your plugin uses decorators. Build, check what you ship, then publish.

<Shell run="build" pack="" publish="" />

The pack command lists the files in the tarball. `tsdown` leaves the packages in `dependencies` and `peerDependencies` as imports, so the built `dist/index.mjs` imports `@seedcord/core/plugin` and `@seedcord/utils` from the install. A scoped name needs `--access public` on the publish command. If you install this package from its tarball in a bot, it passes `seedcord codegen` and `seedcord build`, and the built bot reads its `files` folder through the plugin's `readFiles` call.

If your plugin reads a folder through `readFiles`, tell its users to list that folder in `files`, as the [files page](/writing-plugins/files#reading-data-with-readfiles) shows.

## Test it in a bot first

A plugin that works in your bot's `src/plugins` can break once it moves into its own package. The bot then loads it from `node_modules`, so the plugin has to share the bot's installed copy of `@seedcord/core`. [`attach`](ref:gateway/Seedcord.attach) checks that the plugin extends the [`Plugin`](ref:core/Plugin) class the bot uses. A second copy of `@seedcord/core` defines a second `Plugin`. The plugin extends that one, and `attach` throws `CorePluginFromOtherCore`.

```txt output
Hello doesn't extend the Plugin class your bot uses. That usually means two copies of @seedcord/core are installed. Update the plugin and your @seedcord packages to versions that need the same @seedcord/core. Your package manager can list each installed copy and the package that pulled it in.
```

`seedcord codegen` wraps that message in `Could not import src/bot.ts` with the code `CoreImportFailed`, and `seedcord build` fails with the same error.

<Callout type="warning">

TypeScript can't catch this. It compares the shape of the two `Plugin` classes, and both copies have the same shape. The type check passes in every setup below.

</Callout>

Before you publish, install the packed plugin in a bot and run `tsc` and `seedcord codegen` there.

### Which setups give one copy

These results are for pnpm, with a plugin that lists `@seedcord/core` as a peer dependency and a bot that installs the same version. They don't cover npm or yarn.

{/* prettier-ignore-start */}

| setup | in the bot | copies of `@seedcord/core` | after you change the plugin |
| --- | --- | --- | --- |
| tarball | `pnpm add ../tags/seedcord-plugin-tags-0.1.1.tgz` | one | bump the version, build, pack, add the new file |
| `file:` folder | `pnpm add file:../tags` | one | build, then `pnpm install` |
| workspace | `"seedcord-plugin-tags": "workspace:*"` | one | build the plugin |
| `link:` | `pnpm add link:../tags` | two | switch to a workspace |

{/* prettier-ignore-end */}

pnpm copies a tarball or a `file:` folder into the bot's own `node_modules` and gives the plugin the bot's copy of its peers. In a `workspace:` setup, both packages resolve `@seedcord/core` from the one install the workspace shares. A `link:` points the bot at the plugin folder, so Node resolves `@seedcord/core` from that folder's own `node_modules`, and that is a second copy.

To check your setup, find the `@seedcord/core` that the bot's transport package uses and the one the installed plugin uses, then compare the real paths. Save this as `check.mjs` in the bot and run `node check.mjs`. It reads the transport package as `@seedcord/http`, so write `@seedcord/gateway` in a gateway bot.

```js title="check.mjs"
import { realpathSync } from 'node:fs';
import { findPackageJSON } from 'node:module';
import { pathToFileURL } from 'node:url';

const transport = realpathSync(
    findPackageJSON('@seedcord/http', import.meta.url)
);
const botCore = findPackageJSON(
    '@seedcord/core',
    pathToFileURL(transport).href
);
const pluginCore = findPackageJSON(
    '@seedcord/core',
    import.meta.resolve('seedcord-plugin-tags')
);
console.log(
    realpathSync(botCore) === realpathSync(pluginCore)
        ? 'one copy'
        : 'two copies'
);
```

The script prints `one copy` for the tarball, `file:`, and workspace setups, and `two copies` for `link:`. `pnpm why @seedcord/core` doesn't show this. In the `link:` setup it prints "Found 1 version" for both the bot and the plugin folder because two copies of one version list as one.

### Packing a tarball

Packing a tarball tests exactly what a publish would ship. Bump `version` in the plugin's `package.json` before each pack, like to `0.1.2-dev.0`. pnpm keys a tarball by its file name, so if you pack the same version twice, `pnpm add` installs the first file again.

<Shell run="build" pack="" />

Then install the new file in your bot.

<Shell add="../tags/seedcord-plugin-tags-0.1.2-dev.0.tgz" />

### Telling whether the new code loaded

Press `r` in the terminal running `seedcord dev`. It stops the running bot and starts a new session, which loads `bot.ts` again and runs every plugin's constructor and `init()` again. The status line shows "Starting the bot…" and then the bot's name followed by "is ready!". That status line doesn't mention your plugin, so put a log line in its `init()` while you test, like `this.logger.info('tags v2')`. If the old text still prints after `r`, the old build is still installed.

### Testing in a workspace

In a pnpm workspace, the bot's `node_modules` links to the plugin folder, so a rebuilt `dist` is available without an install. A bot made by `create-seedcord` already has a `pnpm-workspace.yaml`, which holds only pnpm settings. Keep the plugin in a folder inside the bot, like `packages/tags`, and add a `packages` list above those settings. A plugin folder outside the bot can't join that workspace because a workspace has one `pnpm-workspace.yaml`.

```yaml title="pnpm-workspace.yaml"
packages:
    - packages/*
allowBuilds:
    unrs-resolver: false
```

Add `"seedcord-plugin-tags": "workspace:*"` to the bot's dependencies and run `pnpm install`. In the plugin's `devDependencies`, use the same `@seedcord` versions that the bot installs. Build with `pnpm -C packages/tags build`, then press `r`. The `root` in `seedcord.config.ts` is `./src`, so the bot doesn't treat `packages/` as part of its code.

<Callout type="warning">

A [server build](/build/server) leaves your plugin as an import in `dist`, so the built bot loads it from `node_modules`. Deploy it from a tarball, `file:` or workspace install, which give one copy. Don't deploy it from a `link:`.

</Callout>

If your bot file attaches a plugin from your own source, like `src/plugins`, saving the plugin [starts it again](/writing-plugins/hot-reload#saving-the-plugins-own-source) without a restart.

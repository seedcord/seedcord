---
title: Permissions
description: Check the caller's permissions, your bot's permissions, or the caller's role before a handler runs, and reword each refusal.
---

A kick command can fail two ways. The caller might not be allowed to kick, or your bot might not be. If you check by hand, the first is a permissions lookup at the top of every handler. For the second, Discord returns a Missing Permissions error after your handler has already replied or started work.

[`RequirePermissions`](ref:core/RequirePermissions) checks the caller and [`RequireBotPermissions`](ref:core/RequireBotPermissions) checks your bot, both before `execute()` runs. [`RequireRole`](ref:core/RequireRole) checks one role by id.

```ts twoslash title="src/handlers/Kick.ts"
import {
    Gated,
    RequireBotPermissions,
    RequirePermissions,
    SlashHandler,
    SlashRoute
} from '@seedcord/gateway';
import { PermissionFlagsBits } from 'discord.js';

@Gated(
    RequirePermissions([PermissionFlagsBits.KickMembers]),
    RequireBotPermissions([PermissionFlagsBits.KickMembers])
)
@SlashRoute('kick')
export class Kick extends SlashHandler<'kick'> {
    public async execute(): Promise<void> {
        const target = this.options.getUser('target');

        await this.reply(`Kicked ${target.username}.`);
    }
}
```

The two permission gates take a [`PermissionScope`](ref:core/PermissionScope), an array of flag bits. A scope with several bits requires all of them.

```ts twoslash
import { RequirePermissions } from '@seedcord/gateway';
import { PermissionFlagsBits } from 'discord.js';
// ---cut---
RequirePermissions([
    PermissionFlagsBits.ManageMessages,
    PermissionFlagsBits.ManageThreads
]);
```

An http bot doesn't depend on discord.js, so the same bits come from `discord-api-types/v10` there. The values are identical.

## Administrator passes everything

Discord grants every permission to **Administrator**, so both permission gates apply that rule. A caller holding **Administrator** passes any scope you name.

<Callout type="warning">

You hold **Administrator** on your own test server, as the owner or through a role. Both permission gates pass there, so you cannot tell a broken one from a working one. Test with a second account that doesn't have an admin role.

</Callout>

`RequireRole` reads role ids, which is why it also refuses an administrator who lacks the role.

## Channel permissions and server permissions

The `in` option picks which set the gate reads.

```ts twoslash
// @noErrors
import { RequirePermissions } from '@seedcord/gateway';
import { PermissionFlagsBits } from 'discord.js';
// ---cut---
RequirePermissions([PermissionFlagsBits.BanMembers], { in: '
//                                                          ^|
```

{/* prettier-ignore-start */}

| `in` | reads | holds true when |
| --- | --- | --- |
| `'channel'`, the default | the effective set for the invoked channel, after overwrites | Discord would allow the action right here |
| `'guild'` | the base set from roles alone | the roles grant it somewhere in the server |

{/* prettier-ignore-end */}

A channel overwrite can remove a permission that a role granted. `'channel'` includes that overwrite in what it reads, so it answers "can they do this here". `'guild'` answers "do their roles grant this anywhere in the server", which is what you want when the command acts on the whole server.

```ts twoslash
import { RequirePermissions } from '@seedcord/gateway';
import { PermissionFlagsBits } from 'discord.js';
// ---cut---
RequirePermissions([PermissionFlagsBits.BanMembers], {
    in: 'guild'
});
```

<Callout type="transport" only="gateway">

`in: 'guild'` reads role-derived sets that only the gateway cache has. So the gate requires a [`GuildPermissionsContext`](ref:core/GuildPermissionsContext), which the http transport never provides.

</Callout>

Putting a guild-scoped gate on an http handler fails at the decorator line.

```ts twoslash
// @errors: 1238
import {
    Gated,
    RequirePermissions,
    SlashHandler,
    SlashRoute
} from '@seedcord/http';
import { PermissionFlagsBits } from 'discord-api-types/v10';

// ---cut---
@Gated(
    RequirePermissions([PermissionFlagsBits.BanMembers], {
        in: 'guild'
    })
)
@SlashRoute('ban')
export class Ban extends SlashHandler<'ban'> {
    public async execute(): Promise<void> {}
}
```

## On a gateway event handler

An interaction payload has both channel sets. A gateway event doesn't have either one, which changes what `'channel'` does on each gate.

{/* prettier-ignore-start */}

| on an event, `in: 'channel'` | what happens |
| --- | --- |
| `RequirePermissions` | reads the caller's role-derived set, the same value `'guild'` reads. Channel overwrites go uncounted |
| `RequireBotPermissions` | doesn't compile, since it reads `app_permissions` and an event never has it |

{/* prettier-ignore-end */}

Use `in: 'guild'` on an event handler. On the caller side it reads the same set `'channel'` would there, and on the bot side it's the only scope that compiles.

```ts twoslash
import { RequireBotPermissions } from '@seedcord/gateway';
import { PermissionFlagsBits } from 'discord.js';
// ---cut---
RequireBotPermissions([PermissionFlagsBits.ManageMessages], {
    in: 'guild'
});
```

## Requiring a role

[`RequireRole`](ref:core/RequireRole) takes one role id and reads the caller's roles. Roles are server-wide, so it does not take a scope option.

```ts twoslash
import {
    Gated,
    RequireRole,
    SlashHandler,
    SlashRoute
} from '@seedcord/gateway';

// ---cut---
@Gated(RequireRole('221439658686939136'))
@SlashRoute('roles')
export class Roles extends SlashHandler<'roles'> {
    public async execute(): Promise<void> {
        await this.reply('Here they are.');
    }
}
```

Combine several with [`or`](ref:core/or) when holding any one of the roles is enough.

## Replacing each refusal

Each of these gates refuses for more than one reason. It takes one option per reason, and each option takes a `Notice` class you wrote, the same as the `notice` option in [Gates](/checks/gates). seedcord constructs the class with the arguments in the last column.

{/* prettier-ignore-start */}

| gate | option | refuses when | constructed with |
| --- | --- | --- | --- |
| `RequirePermissions` | `notInGuild` | the call came from outside a server | nothing |
| `RequirePermissions` | `unresolved` | the member's set is missing inside a server | nothing |
| `RequirePermissions` | `missing` | a bit in the scope is absent | `null` for the caller, then the missing names |
| `RequireBotPermissions` | `notInGuild` | the call came from outside a server | nothing |
| `RequireBotPermissions` | `missing` | a bit in the scope is absent from your bot's set | `'The bot'`, then the missing names |
| `RequireRole` | `notInGuild` | the call came from outside a server | nothing |
| `RequireRole` | `missingRole` | the caller lacks the role | the role id |

{/* prettier-ignore-end */}

```ts twoslash
import { RequirePermissions, RequireRole } from '@seedcord/gateway';
import { PermissionFlagsBits } from 'discord.js';

import type {
    NoticeConstructor,
    PermissionNoticeConstructor
} from '@seedcord/gateway';

declare const OutsideServer: NoticeConstructor;
declare const CannotBan: PermissionNoticeConstructor;
declare const SubscribersOnly: NoticeConstructor<[roleId: string]>;
// ---cut---
RequirePermissions([PermissionFlagsBits.BanMembers], {
    notInGuild: OutsideServer,
    missing: CannotBan
});

RequireRole('221439658686939136', { missingRole: SubscribersOnly });
```

Without the option, a gate uses the default card. The permission gates list every missing bit on it by name, and `RequireRole` mentions the role.

A check these gates don't cover, like whether the caller linked an account, is [a gate you write yourself](/checks/your-own).

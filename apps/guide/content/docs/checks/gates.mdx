Most handlers open with the same few checks. Is this a server? Can this person ban? If you write those checks inside `execute()`, every handler starts with its own copy of them. If you forget to copy one into a handler, that command runs for anyone.

A gate puts that check on the class and runs before `execute()`. If it passes, your handler runs, and if it refuses, the call stops there. Attach one with [`@Gated`](ref:gateway/Gated), above the route decorator. The `Ban` handler below runs only for someone in a server who holds `BanMembers`.

```ts twoslash title="src/handlers/Ban.ts"
import {
    Gated,
    GuildOnly,
    RequirePermissions,
    SlashHandler,
    SlashRoute
} from '@seedcord/gateway';
import { PermissionFlagsBits } from 'discord.js';

@Gated(
    GuildOnly(),
    RequirePermissions([PermissionFlagsBits.BanMembers])
)
@SlashRoute('ban')
export class Ban extends SlashHandler<'ban'> {
    public async execute(): Promise<void> {
        const target = this.options.getUser('target');

        await this.reply(`Banned ${target.username}.`);
    }
}
```

`execute()` runs once both gates pass. `GuildOnly()` refuses a call from a DM, and `RequirePermissions` refuses a caller without `BanMembers`.

## A gate refuses by throwing

seedcord catches a gate's throw at the same boundary it catches your handler's. The user sees the same card either way. [Refusing a request](/replying/throwing) covers what each class produces.

Every gate in the table below throws a [`Notice`](ref:core/Notice) except [`IgnoreBots`](ref:gateway/IgnoreBots), which throws a [`Silence`](ref:core/Silence). seedcord stops handling the message, so your bot doesn't reply.

## Several gates on one handler

`@Gated` takes one gate or several, and all of them have to pass. They run left to right, and the first one to refuse stops the rest.

The order you pick matters once a gate does something costly, like reading a database. Put the cheap checks first, so a caller who fails one never reaches the read behind it.

A second `@Gated` on the same class adds its gates to the list. TypeScript applies class decorators from the bottom up, so the one nearer the class runs first. One `@Gated` with every gate in it keeps the order where you can read it.

## The catalog gates

{/* prettier-ignore-start */}

| gate | passes when |
| --- | --- |
| [`OwnerOnly()`](ref:core/OwnerOnly) | the caller's id is in `ownerIds` |
| [`GuildOnly()`](ref:core/GuildOnly) | the call came from a server |
| [`DmOnly()`](ref:core/DmOnly) | the call came from a direct message |
| [`RequireRole(id)`](ref:core/RequireRole) | the caller holds that role |
| [`RequirePermissions(bits)`](ref:core/RequirePermissions) | the caller holds every bit you pass |
| [`RequireBotPermissions(bits)`](ref:core/RequireBotPermissions) | your bot holds every bit you pass |
| [`Cooldown(duration)`](ref:core/Cooldown) | the current window still has uses left |
| [`Nsfw()`](ref:gateway/Nsfw) | the channel is age-restricted. Gateway interaction handlers only, modals excluded |
| [`IgnoreBots`](ref:gateway/IgnoreBots) | the actor is a person. Gateway only, and event handlers only |
| [`MentionPrefix`](ref:gateway/MentionPrefix) | the message starts with a mention of your bot, like `@bot ping`. `messageCreate` and `messageUpdate` handlers only |

{/* prettier-ignore-end */}

<Callout type="transport" only="gateway">

`Nsfw`, `IgnoreBots`, and `MentionPrefix` ship in `@seedcord/gateway` alone. `Nsfw` reads the discord.js channel object on the interaction. `IgnoreBots` and `MentionPrefix` attach to event handlers, which an http bot doesn't have.

</Callout>

Most of these are functions, so you call one and pass the result. `IgnoreBots` doesn't take options, so you attach it directly.

```ts twoslash title="src/events/Mentioned.ts"
import {
    EventHandler,
    Gated,
    IgnoreBots,
    RegisterEvent
} from '@seedcord/gateway';
import { Events } from 'discord.js';

@Gated(IgnoreBots)
@RegisterEvent([Events.MessageCreate])
export class Mentioned extends EventHandler<Events.MessageCreate> {
    public async execute(): Promise<void> {
        const [message] = this.event;

        await message.reply('hey');
    }
}
```

Every gate has the context it reads, and `@Gated` checks that against the handler you put it on. `Nsfw()` reads an interaction's channel, so attaching it to the event handler below fails to compile. The error shows the gate and the handler kind.

```ts twoslash
// @errors: 1238
import {
    EventHandler,
    Gated,
    Nsfw,
    RegisterEvent
} from '@seedcord/gateway';
import { Events } from 'discord.js';

// ---cut---
@Gated(Nsfw())
@RegisterEvent([Events.MessageCreate])
export class Welcome extends EventHandler<Events.MessageCreate> {
    public async execute(): Promise<void> {}
}
```

### Who counts as an owner

`OwnerOnly` fits a command only you should run, like a reload or a shutdown. It reads `ownerIds` from your bot config, and with that key unset it refuses _everyone_.

```ts twoslash title="src/bot.ts"
import { resolve } from 'node:path';

import { Seedcord } from '@seedcord/gateway';
import { GatewayIntentBits } from 'discord.js';

export const seedcord = new Seedcord({
    ownerIds: ['221439658686939136'],
    bot: {
        clientOptions: { intents: [GatewayIntentBits.Guilds] },
        interactions: {
            path: resolve(import.meta.dirname, './handlers')
        },
        commands: {
            path: resolve(import.meta.dirname, './commands')
        },
        events: { path: null }
    },
    subscribers: { path: null }
});
```

`OwnerOnly` reads `ownerIds` again on every check. If you assign `seedcord.config.ownerIds` after the bot exists, say from a settings file, the next check uses the new list.

## Replacing a refusal

Each refusal card uses seedcord's default wording. Replace it when your command has a next step to offer, like pointing someone at the server where it works.

`OwnerOnly`, `GuildOnly`, `DmOnly`, and `Nsfw` take the same [`GateNoticeOptions`](ref:core/GateNoticeOptions). Pass a [`Notice`](ref:core/Notice) class you wrote as `notice` to make the gate throw it in place of its own.

```ts twoslash
import {
    BuilderComponent,
    Notice,
    OwnerOnly
} from '@seedcord/gateway';

import type { ReplyResponse } from '@seedcord/gateway';

class LockedCard extends BuilderComponent<'container'> {
    public constructor() {
        super('container');

        this.instance.addTextDisplayComponents((text) =>
            text.setContent('### Locked\nAsk a maintainer.')
        );
    }
}

class Locked extends Notice {
    public constructor() {
        super('caller is not a maintainer');
    }

    public override render(): ReplyResponse {
        return { components: [new LockedCard().component] };
    }
}

// ---cut---
OwnerOnly({ notice: Locked });
```

A gate that can refuse for more than one reason takes a class per reason. `RequirePermissions` takes `notInGuild`, `unresolved`, and `missing`. seedcord constructs each class with that refusal's data, so `missing` gets the permission names and `Cooldown`'s `notice` gets `resetAt`, the time in milliseconds when the caller can try again. Each gate in [the catalog table](#the-catalog-gates) links to its API page, which lists every option it takes.

[Permissions](/checks/permissions) takes the permission gates in turn, including what Administrator does to them. When none of the shipped gates fits, you can [write your own](/checks/your-own) or [combine several into one](/checks/combining).

title: Interaction middleware
description: Running ahead of your handler over the same reply surface, a middleware stops the whole dispatch when it throws.
---

A middleware runs before your handler. Write one when several handlers all need the same thing done first, like loading the caller's record, or when you want to turn an interaction away before it reaches your code.

On every dispatch seedcord builds the handler, runs the middleware chain, then runs that handler's gates, and finally the handler itself.

```ts twoslash title="src/handlers/middlewares/Trace.ts"
import {
    InteractionMiddleware,
    RegisterInteractionMiddleware
} from '@seedcord/gateway';

@RegisterInteractionMiddleware()
export class Trace extends InteractionMiddleware {
    public async execute(): Promise<void> {
        this.logger.debug(`reached ${this.dispatch.routeId}`);
        await Promise.resolve();
    }
}
```

You can omit the options object on [`@RegisterInteractionMiddleware`](ref:core/RegisterInteractionMiddleware) entirely, the way `Trace` does. Both of its keys are optional on their own too. Omitting them runs the middleware on every kind that carries a reply target.

## Which interactions it runs for

You write the kinds twice, once in `{ kinds }` and once in the generic on [`InteractionMiddleware`](ref:gateway/InteractionMiddleware). The two have to agree. Where they differ, applying the decorator is a compile error whose message says which side is missing a kind.

```ts twoslash title="src/handlers/middlewares/ClickLog.ts"
import {
    InteractionKind,
    InteractionMiddleware,
    RegisterInteractionMiddleware
} from '@seedcord/gateway';
// ---cut---
@RegisterInteractionMiddleware({ kinds: [InteractionKind.Button] })
export class ClickLog extends InteractionMiddleware<InteractionKind.Button> {
    public async execute(): Promise<void> {
        const clicked = this.event;
        //    ^?
        this.logger.debug(`clicked ${clicked.customId}`);
        await Promise.resolve();
    }
}
```

`this.event` follows the generic, which is why `customId` is there to read. Naming several kinds gives you a union of those payloads.

```ts twoslash title="src/handlers/middlewares/ComponentTrace.ts"
import {
    InteractionKind,
    InteractionMiddleware,
    RegisterInteractionMiddleware
} from '@seedcord/gateway';
// ---cut---
@RegisterInteractionMiddleware({
    kinds: [InteractionKind.Button, InteractionKind.Modal]
})
export class ComponentTrace extends InteractionMiddleware<
    InteractionKind.Button | InteractionKind.Modal
> {
    public async execute(): Promise<void> {
        this.logger.debug(`component on ${this.dispatch.routeId}`);
        await Promise.resolve();
    }
}
```

Every kind seedcord routes is a member of [`InteractionKind`](ref:core/InteractionKind). Autocomplete is the one a middleware cannot list, since Discord accepts only a list of choices in reply to one.

<Callout type="transport">

`this.event` is a discord.js interaction on gateway and the payload Discord posted on http. A button's id reads `this.event.customId` on the first and `this.event.data.custom_id` on the second. A union narrows through the discord.js guards on gateway, and through `type` and `data.component_type` on http.

</Callout>

## Order

`priority` takes any finite number and decides the order, with lower running earlier. Leaving it out puts the middleware at `0`.

Two middleware sharing a number run in the order seedcord loaded them. Give anything order-dependent a number of its own.

A negative priority puts a middleware ahead of every one that took the default.

## Stopping the dispatch

Throwing from `execute()` ends the dispatch before the handler or its gates run.

What you throw decides what the caller sees. A [`Notice`](ref:core/Notice) renders its card. A [`Silence`](ref:core/Silence) drops the interaction with no reply, so the caller sees Discord's own failed-interaction message. Anything else reports as a fault, the same as a throw from a handler.

```ts twoslash title="src/handlers/middlewares/Maintenance.ts"
import {
    InteractionMiddleware,
    RegisterInteractionMiddleware
} from '@seedcord/gateway';

import type { Notice } from '@seedcord/gateway';

declare const Closed: new () => Notice;
declare function underMaintenance(): Promise<boolean>;
// ---cut---
@RegisterInteractionMiddleware({ priority: -10 })
export class Maintenance extends InteractionMiddleware {
    public async execute(): Promise<void> {
        if (await underMaintenance()) throw new Closed();
    }
}
```

`Closed` is a [`Notice` you write yourself](/replying/throwing), with its own `render()`.

## Replying from a middleware

A middleware holds the reply surface its handler built. `reply`, `defer`, `followUp`, `edit`, `send`, and `delete` all read the one ack state.

**A middleware that acks leaves its handler an acknowledged interaction.** `send()` carries on working there, since it picks whichever verb the current state allows. A `reply()` after the ack throws [`ReplyIllegalAckState`](/replying/ack-states).

<Callout type="warning">

seedcord builds your handler before the chain and the gates run. A constructor that queries your database therefore runs that query even when a middleware or a gate refuses the interaction. Keep the constructor to assigning fields and put the work in `execute()`.

</Callout>

## After the handler runs

seedcord calls `after()` in reverse once the dispatch ends, newest middleware first. It records a middleware as its `execute()` begins, so a middleware that throws still gets its `after()`. The ones behind it in the chain never started, and they get none.

Nothing skips those calls. A gate refusal, a handler that threw, and a card whose `render()` threw while answering that refusal all still run them. Use `after()` to release whatever `execute()` held open, a lock or a tracing span.

```ts twoslash hovers title="src/handlers/middlewares/Span.ts"
import {
    InteractionMiddleware,
    RegisterInteractionMiddleware
} from '@seedcord/gateway';

import type { DispatchResult } from '@seedcord/gateway';

declare const tracer: {
    open(route: string): { end(status: string): void };
};
// ---cut---
@RegisterInteractionMiddleware()
export class Span extends InteractionMiddleware {
    private span?: ReturnType<(typeof tracer)['open']>;

    public async execute(): Promise<void> {
        this.span = tracer.open(this.dispatch.routeId);
        await Promise.resolve();
    }

    public override async after(
        result: DispatchResult
    ): Promise<void> {
        this.span?.end(result.outcome);
        await Promise.resolve();
    }
}
```

The base declares `after()` optional, so your implementation has to carry `override`. Leaving it off is a compile error.

[`DispatchResult`](ref:core/DispatchResult) reports how the dispatch ended. `outcome` reads `handled`, `refused`, or `failed`. Both failure states carry the thrown value on `caught`.

A throw inside `after()` reaches the log and stops there. The rest of the chain still runs.

## Where middleware lives

seedcord loads middleware from `bot.interactions.middlewares`. The key is optional.

```ts twoslash title="src/bot.ts"
import { resolve } from 'node:path';

import { Seedcord } from '@seedcord/gateway';
import { GatewayIntentBits } from 'discord.js';

const rest = {
    commands: { path: null },
    events: { path: null }
} as const;
// ---cut---
export const seedcord = new Seedcord({
    bot: {
        ...rest,
        clientOptions: { intents: [GatewayIntentBits.Guilds] },
        interactions: {
            path: resolve(import.meta.dirname, './handlers'),
            middlewares: resolve(
                import.meta.dirname,
                './handlers/middlewares'
            )
        }
    },
    subscribers: { path: null }
});
```

A class in that directory without the decorator loads and never runs, the same way a handler missing its route decorator does. That one is caught while you write by `@seedcord/middleware-missing-register-decorator`.

A middleware passes values to the handler and its gates through [the dispatch context](/gates/dispatch-context).

Most bots need something beside Discord, like a database, a cache, or a client for another API. Wiring one up by hand means starting it before the bot logs in, handing it to every handler through a global or an import, and stopping it on shutdown before the process exits.

A plugin packages that work. It starts and stops at defined points in your bot's lifecycle and takes its own options. You attach it under a key you pick, then read it from `this.core` anywhere `core` is available, like a handler.

```ts twoslash hovers title="src/bot.ts"
import { Seedcord } from '@seedcord/gateway';
import { Mongoose } from '@seedcord/plugin-mongoose';
import { GatewayIntentBits } from 'discord.js';

export const seedcord = new Seedcord({
    bot: {
        clientOptions: { intents: [GatewayIntentBits.Guilds] },
        interactions: { path: './handlers' },
        commands: { path: './commands' },
        events: { path: null }
    },
    subscribers: { path: null }
}).attach('db', Mongoose, {
    path: './services',
    uri: 'mongodb://localhost:27017/',
    name: 'seedcord'
});

export default seedcord;
```

[`attach`](ref:gateway/Seedcord.attach) takes the key, the plugin class, and whatever that class's constructor takes after the bot. seedcord passes the bot itself. If the constructor takes only the bot, attach it with two arguments.

Mongoose reads its `path` relative to `root` in [`seedcord.config.ts`](/build/config), like the bot's own `path` keys. With `root: './src'`, the `'./services'` above means `src/services`. It reads the folder when the bot starts, and again during `seedcord codegen`. That read throws if the folder breaks one of these rules:

{/* prettier-ignore-start */}

| if the folder | it throws |
| --- | --- |
| is outside `root` | `CorePathOutsideRoot` |
| is inside a dot-folder, `node_modules`, your `outDir`, or the logs folder | `CoreDirectorySkipped` |
| is relative in a test or `tsx` script, which has no `root` | `CoreDirectoryRootUnknown`. Pass an absolute path there |

{/* prettier-ignore-end */}

Keep `bot.ts` exporting the bot as its default export, the way the sample does. `seedcord dev`, `build`, and `codegen` load your bot from it and stop with `CliInstanceInvalid` without one.

## Reading it from a handler

`this.core` has every attached plugin under its key.

```ts twoslash title="src/handlers/History.ts"
import { SlashHandler, SlashRoute } from '@seedcord/gateway';
import {
    MongooseService,
    RegisterMongooseService
} from '@seedcord/plugin-mongoose';
import mongoose from 'mongoose';

import type {
    Mongoose,
    MongooseDocument
} from '@seedcord/plugin-mongoose';

interface IUser extends MongooseDocument {
    username: string;
}

@RegisterMongooseService('users')
class Users extends MongooseService<IUser> {
    public static schema = new mongoose.Schema<IUser>({
        username: { type: String, required: true }
    });

    public findByName(username: string) {
        return this.model.findOne({ username }).exec();
    }
}

declare module '@seedcord/gateway' {
    interface Core {
        db: Mongoose;
    }
    interface PluginTypes {
        '@seedcord/plugin-mongoose': {
            services: { users: typeof Users };
        };
    }
}

// ---cut---
@SlashRoute('history')
export class History extends SlashHandler<'history'> {
    public async execute(): Promise<void> {
        const found =
            await this.core.db.services.users.findByName('ada');

        await this.reply(
            found ? `Found ${found.username}.` : 'No record.'
        );
    }
}
```

In `History`, you reach the Mongoose service through `this.core.db`.

The sample hides the lines that `seedcord codegen` writes into `src/seedcord-gen.ts` in your project. With them, `services.users` is typed as your `Users` service, so `findByName` type-checks.

## Attaching more than one

A bot can attach more than one plugin, each under its own key. Chain another `attach` for each one. The plugins start one after another, in the order you attached them, unless one [moves its `init()` to another phase](/plugins/lifecycle#moving-a-method-to-another-phase). If your plugin's `init()` reads another plugin, attach that one first. Otherwise your `init()` runs before the other plugin has started.

```ts twoslash
import { Seedcord } from '@seedcord/gateway';
import { Kysely } from '@seedcord/plugin-kysely';
import { Mongoose } from '@seedcord/plugin-mongoose';
import Database from 'better-sqlite3';
import { GatewayIntentBits } from 'discord.js';
import { SqliteDialect } from 'kysely';

export const seedcord = new Seedcord({
    bot: {
        clientOptions: { intents: [GatewayIntentBits.Guilds] },
        interactions: { path: './handlers' },
        commands: { path: './commands' },
        events: { path: null }
    },
    subscribers: { path: null }
})
    .attach('db', Mongoose, {
        path: './mongo',
        uri: 'mongodb://localhost:27017/',
        name: 'seedcord'
    })
    .attach('sql', Kysely, {
        path: './sql',
        dialect: () =>
            new SqliteDialect({ database: new Database('bot.db') }),
        migrations: { path: './migrations' }
    });
```

### Grouping plugins under one name

A class you write as a [`Plugin`](ref:core/Plugin) takes its own key on `core` too. Ten of them means ten keys on `core`, in one list with your database.

Put a dot in the key to move a plugin out of that list and into a group.

```ts twoslash
import { Plugin, Seedcord } from '@seedcord/gateway';

// ---cut-start---
declare const seedcord: Seedcord;

class Users extends Plugin {
    public async init(): Promise<void> {}
}

class Tickets extends Plugin {
    public async init(): Promise<void> {}
}
// ---cut-end---
export default seedcord
    .attach('app.users', Users)
    .attach('app.tickets', Tickets);
```

`app` here is a plain object on `core`. Each plugin takes the key after the dot, so in a handler you read one as `this.core.app.users`. seedcord still starts both in attach order and stops them during shutdown.

A key can have only one dot. `seedcord codegen` writes one entry for the group, and that entry types every plugin inside it.

A name holds one plugin or one group. If `app.users` exists, attaching a plugin at `app` fails to compile. Nesting under `db`, which already holds your database, fails the same way.

```ts twoslash
// @errors: 2345
import { Plugin, Seedcord } from '@seedcord/gateway';

declare const seedcord: Seedcord;

class Users extends Plugin {
    public async init(): Promise<void> {}
}

class Tickets extends Plugin {
    public async init(): Promise<void> {}
}
// ---cut---
seedcord.attach('app.users', Users).attach('app', Tickets);
```

## No plugin types in your handler?

`this.core.db` has the type `Mongoose` in `History` because the first sample exports what `attach` returns. If you call `attach` as a statement and then export `seedcord` itself, the plugin still starts. TypeScript loses its type since nothing keeps the type that call returns.

```ts twoslash hovers
// @errors: 2339
import { Seedcord } from '@seedcord/gateway';
import { Mongoose } from '@seedcord/plugin-mongoose';

declare const config: ConstructorParameters<typeof Seedcord>[0];
declare const options: ConstructorParameters<typeof Mongoose>[1];

// ---cut---
const seedcord = new Seedcord(config);
seedcord.attach('db', Mongoose, options);

type Db = (typeof seedcord)['db'];
```

The last line is the lookup codegen writes into `src/seedcord-gen.ts`, so a type check reports this error in that file. `this.core.db` compiles as `any` in your handlers until you fix the export. Your editor stops offering `services`, and a typo like `this.core.db.servics` still compiles.

## The key is also a log channel

A plugin logs on the channel named after its attach key. The Mongoose plugin above logs on `db`. You can then [filter or silence](/built-ins/logger-config#one-channel-at-a-time) one plugin's logs by the key you gave it. A grouped plugin keeps its whole key, dot included, as its channel. seedcord already logs on reserved channels of its own, so those names can't be keys.

```ts twoslash
// @errors: 2345
import { Seedcord } from '@seedcord/gateway';
import { Mongoose } from '@seedcord/plugin-mongoose';
import { GatewayIntentBits } from 'discord.js';

const seedcord = new Seedcord({
    bot: {
        clientOptions: { intents: [GatewayIntentBits.Guilds] },
        interactions: { path: './handlers' },
        commands: { path: './commands' },
        events: { path: null }
    },
    subscribers: { path: null }
});

// ---cut---
seedcord.attach('commands', Mongoose, {
    path: './services',
    uri: 'mongodb://localhost:27017/',
    name: 'seedcord'
});
```

<Callout type="warning">

`commands` is one of those reserved channels, so the `attach` above fails to compile. If the key is only known at run time, like one read from an environment variable, `attach` throws `CorePluginReservedChannel` when it runs. [Logging](/built-ins/logging) lists the reserved channels with what each one holds.

</Callout>

## When attach throws

`attach` throws in these cases when it runs:

{/* prettier-ignore-start */}

| if | it throws |
| --- | --- |
| startup has begun, like when a startup task calls `attach`, or an edge bot has taken its first request | `CorePluginAfterInit` |
| another plugin or seedcord itself already uses the key on `core`, like `bus` | `CorePluginKeyExists` |
| you nest under a name the bot already uses, like `db` | `CorePluginGroupTaken` |
| you attach a plugin at a name that holds a group | `CorePluginKeyHoldsGroup` |
| the key has an empty part or a second dot | `CorePluginKeyMalformed` |
| the plugin extends [`Plugin`](ref:core/Plugin) from a second copy of `@seedcord/core`, usually because the plugin and your `@seedcord` packages need different versions of it | `CorePluginFromOtherCore` |

{/* prettier-ignore-end */}

## A plugin declares where it runs

Some plugins only work in one setup, like one that reads discord.js objects, since only a gateway bot has those. A plugin declares the transport it supports, `'gateway'`, `'http'`, or `'any'`, and the runtime it supports. A gateway bot and an http bot on Node or Bun run on a `'server'`. An http bot on Cloudflare Workers runs on the `'edge'`. The base class a plugin extends sets both defaults, and [a plugin can narrow them](/writing-plugins/runtimes):

{/* prettier-ignore-start */}

| base class | transport | runtime |
| --- | --- | --- |
| `Plugin` from `@seedcord/gateway` | `'gateway'` | `'server'` |
| `Plugin` from `@seedcord/http` | `'http'` | `'any'` |
| `Plugin` from `@seedcord/core/plugin` | `'any'` | `'any'` |

{/* prettier-ignore-end */}

A plugin that declares `'any'` attaches to any bot. One that extends the gateway `Plugin` attaches to a gateway bot only. Extend the `@seedcord/core/plugin` one for a plugin that works on both transports.

If you attach a plugin to a bot that doesn't match, TypeScript reports the mismatch in your editor before the bot runs.

```txt output
this plugin declares transport 'gateway' but this bot runs 'http'
this plugin declares runtime 'server' but this bot runs 'edge'
```

A bot on Cloudflare Workers attaches plugins the same way as any other bot, with `attach` in `bot.ts`. If a plugin declares the `'server'` runtime, like [Mongoose](/plugins/mongoose), a Workers bot gets the runtime message above. Each plugin's page says where it runs. A plugin from the `@seedcord/http` or `@seedcord/core/plugin` base attaches there unless it limits `runtime`.

A cast, or a plain JavaScript bot, gets past the types. `attach` then throws `CorePluginScopeMismatch` when it runs, with the plugin's name and the transport or runtime that differs. [Workers](/build/workers) covers setting that bot up.

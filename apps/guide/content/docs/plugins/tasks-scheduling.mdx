---
title: Scheduling jobs
description: Run a function later, like an unban a day after a tempban, and keep the job in a kv driver so it still runs after a restart.
---

Some work has to run later, like lifting a ban a day after `/tempban`. With `setTimeout`, that unban was a timer in your bot's memory, and any restart before it ran lost it.

[`schedule()`](ref:plugin-tasks/Tasks.schedule) writes the job to your [kv store](/built-ins) before it sets a timer. With a [driver](/built-ins/drivers) that keeps its records, the job is still there after a restart. This page assumes the [tasks plugin](/plugins/tasks) is attached under the key `tasks`. A handler then reaches it as [`this.core.tasks`](/plugins#reading-it-from-a-handler) once you've run [`seedcord codegen`](/plugins/typing).

## Writing a scheduled task

A scheduled task is usually a [`Task`](ref:plugin-tasks/Task) in your `path` folder with no pattern. Its type argument declares the data it takes.

```ts twoslash title="src/tasks/Unban.ts"
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';

interface UnbanData {
    guildId: string;
    userId: string;
}

@RegisterTask()
export class Unban extends Task<UnbanData> {
    public async execute(): Promise<void> {
        const { guildId, userId } = this.data;
        const guild =
            await this.core.bot.client.guilds.fetch(guildId);

        await guild.bans.remove(userId);
    }
}
```

`this.data` has the type `UnbanData`. A task with a pattern can't declare data, because nothing passes data to a cron run.

```ts twoslash
// @errors: 1238
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';
// ---cut---
@RegisterTask('* * * * *')
export class Unban extends Task<{
    guildId: string;
    userId: string;
}> {
    public async execute(): Promise<void> {}
}
```

Pass ids in `data`, like `guildId` and `userId`, and fetch what you need when the task runs. The job may run days later, so a copy of a member or a guild taken today is out of date by then.

## Scheduling a job

`schedule()` takes the class and exactly one of two times. `in` takes a duration, and `at` takes a `Date` or a timestamp in milliseconds.

```ts twoslash title="src/handlers/TempBan.ts"
// ---cut-start---
// @filename: tasks/Unban.ts
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';

@RegisterTask()
export class Unban extends Task<{
    guildId: string;
    userId: string;
}> {
    public async execute(): Promise<void> {}
}

// @filename: handlers/TempBan.ts
import type { Tasks } from '@seedcord/plugin-tasks';

declare module '@seedcord/gateway' {
    interface Core {
        tasks: Tasks;
    }
    interface SlashRegistry {
        tempban: {
            options: { target: { kind: 'user'; required: true } };
            cache: 'cached';
        };
    }
}
// ---cut-end---
import { SlashHandler, SlashRoute } from '@seedcord/gateway';

import { Unban } from '../tasks/Unban';

@SlashRoute('tempban')
export class TempBan extends SlashHandler<'tempban'> {
    public async execute(): Promise<void> {
        const { guild, guildId } = this.event;
        const userId = this.options.getUser('target').id;

        await guild.bans.create(userId);

        const job = await this.core.tasks.schedule(Unban, {
            //  ^?
            in: '1d',
            data: { guildId, userId }
        });

        await this.core.kv
            .collection<string>('unban-job')
            .set(userId, job.id);

        await this.reply('Banned for a day.');
    }
}
```

`job` is a [`ScheduledJob`](ref:plugin-tasks/ScheduledJob), and `TempBan` keeps its `id` to cancel it later. TypeScript checks `'1d'` against [`ValidDuration`](ref:utils/ValidDuration), which takes `ms`, `s`, `m`, `h`, or `d` after a whole number above 0. `data` follows the type on `Unban`, which means a missing `userId` fails to compile. `data` on a task that declares none fails too.

Await `schedule()`, because it resolves once your driver holds the job. If the driver can't store it, the call throws `CoreKvDriverFailed`, and no job exists.

{/* prettier-ignore-start */}

| if you pass | it throws |
| --- | --- |
| a `string` for `in` that isn't a duration | `InvalidDuration` |
| an `in` so long it ends after the year 275760 | `PluginTasksDurationTooLong` |
| an invalid `Date`, `NaN`, `0`, or a negative number for `at` | `PluginTasksInvalidDate` |
| a number for `at` from before the year 2000 | `PluginTasksAtInSeconds` |
| a class the plugin didn't load from `path` | `PluginTasksNotLoaded` |

{/* prettier-ignore-end */}

`Date.now()` counts milliseconds, while a Unix timestamp from another API usually counts seconds. Read as milliseconds, that timestamp is a date in January 1970, which is why `schedule()` throws `PluginTasksAtInSeconds` for it. Any other time in the past runs the job right away.

`schedule()` also takes a cron task that declares no data. The job adds one extra run at that time. If `protect` is on and a run from the pattern is still running at that time, the job waits for it to end and then runs. A job of a paused task runs on time.

## Cancelling a job

A moderator lifts the ban today, and tomorrow's job is still stored. If nothing cancels it, it runs anyway. `TempBan` stored the job's `id` in the `unban-job` collection under the user's id.

```ts twoslash title="src/handlers/LiftBan.ts"
import { SlashHandler, SlashRoute } from '@seedcord/gateway';
// ---cut-start---
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';

import type { Tasks } from '@seedcord/plugin-tasks';

declare module '@seedcord/gateway' {
    interface Core {
        tasks: Tasks;
    }
    interface SlashRegistry {
        unban: {
            options: { target: { kind: 'user'; required: true } };
            cache: 'cached';
        };
    }
}
// ---cut-end---

@SlashRoute('unban')
export class LiftBan extends SlashHandler<'unban'> {
    public async execute(): Promise<void> {
        const userId = this.options.getUser('target').id;
        const jobs = this.core.kv.collection<string>('unban-job');
        const jobId = await jobs.get(userId);

        if (jobId !== undefined) {
            await this.core.tasks.cancel(jobId);
            await jobs.delete(userId);
        }

        await this.event.guild.bans.remove(userId);
        await this.reply('Unbanned.');
    }
}
```

`LiftBan` reads the id from `unban-job` and passes it to [`cancel()`](ref:plugin-tasks/Tasks.cancel), which deletes the job from your driver and resolves to `true`. It resolves to `false` if no job has that id, or if the job's time has come, including a job that's waiting for an earlier run to end. A cancel that arrives after the run started doesn't stop that run.

[`jobs()`](ref:plugin-tasks/Tasks.jobs) returns a `ScheduledJob` for each job waiting to run in this process.

## What JSON can store

The plugin stores a job in your driver as JSON, and after a restart `execute()` gets back only what JSON can hold. `data` has to fit, and [`this.data`](ref:plugin-tasks/Task.data) has the type of what comes back.

```ts twoslash title="src/tasks/Remind.ts"
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';
// ---cut---
@RegisterTask()
export class Remind extends Task<{ text: string; sentAt: Date }> {
    public async execute(): Promise<void> {
        const { sentAt } = this.data;
        //      ^?
        this.logger.info(new Date(sentAt).toISOString());
    }
}
```

You pass `sentAt` as a `Date`, and it reads back as a `string`, so `Remind` builds a `Date` again before using it. A value with no JSON form, like a `Map`, a `Set`, a function, or a `bigint`, fails to compile.

```ts twoslash
// @errors: 2322
// ---cut-start---
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';

import type { Tasks } from '@seedcord/plugin-tasks';

declare const tasks: Tasks;
// ---cut-end---
@RegisterTask()
export class Tally extends Task<{ counts: Map<string, number> }> {
    public async execute(): Promise<void> {}
}

await tasks.schedule(Tally, {
    in: '1h',
    data: { counts: new Map() }
});
```

A circular reference still compiles. Your kv store throws `CoreKvUnserializable` for it, and `schedule()` doesn't store the job.

## Keeping jobs through a restart

The kv store keeps its records in memory until you give it a [driver](/built-ins/drivers), and a restart clears that memory along with your jobs. The first time you schedule a job into it, the plugin logs a warning. To keep your jobs, set `kv` on your `Seedcord` config.

```ts twoslash title="src/bot.ts"
import KeyvSqlite from '@keyv/sqlite';
import { KeyvDriver, Seedcord } from '@seedcord/gateway';
import { Tasks } from '@seedcord/plugin-tasks';
import { GatewayIntentBits } from 'discord.js';
import Keyv from 'keyv';

export const seedcord = new Seedcord({
    kv: new KeyvDriver(
        new Keyv(new KeyvSqlite('sqlite://./kv.sqlite'))
    ),
    bot: {
        clientOptions: { intents: [GatewayIntentBits.Guilds] },
        interactions: { path: './handlers' },
        commands: { path: './commands' },
        events: { path: null }
    },
    subscribers: { path: null }
}).attach('tasks', Tasks, { path: './tasks' });

export default seedcord;
```

With `kv` set, the plugin reads every job back from `kv.sqlite` during startup. It sets their timers once the bot has logged in, and a job that came due during the restart runs as soon as the bot is ready.

<Callout type="warning">

The driver has to [list its keys](/built-ins#reading-every-record), because that's how the plugin finds your jobs at startup. A cache adapter like `@keyv/memcache` can't, so `init()` throws `CoreKvKeysUnsupported` and the bot doesn't start.

</Callout>

<Callout type="warning">

The plugin stores jobs under the key you pass to `attach`, here `'tasks'`. If you change that key, the plugin can't find the jobs stored under `tasks`, and they never run.

</Callout>

### A job can run twice

The plugin deletes a job after its run ends. If the process dies during a run, the job is still in your driver and runs again after the restart. The same happens if shutdown aborts `this.signal` and the task then throws. Deleting the job before the run would lose it in a crash.

Write a scheduled task to make a second run harmless, because the plugin doesn't remove duplicates for you. `Unban` is close to safe. A second run gets Discord's [`Unknown Ban` error](https://discord.com/developers/docs/topics/opcodes-and-status-codes#json) and changes nothing, though the plugin still publishes the throw as a failed `taskRan`. A task that sends a DM isn't safe to run twice. Record each DM in [`core.kv`](/built-ins) and check that record first.

If a task throws for any other reason, the plugin deletes the job without running it again, since a task that fails on its data would otherwise fail forever. To retry, call `schedule()` from [`onError()`](ref:plugin-tasks/Task.onError).

```ts twoslash title="src/tasks/Unban.ts"
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';
// ---cut-start---
import type { Tasks } from '@seedcord/plugin-tasks';

declare module '@seedcord/gateway' {
    interface Core {
        tasks: Tasks;
    }
}
// ---cut-end---

@RegisterTask()
export class Unban extends Task<{ userId: string }> {
    public async execute(): Promise<void> {
        this.logger.info(`Unbanning ${this.data.userId}`);
    }

    public override async onError(): Promise<void> {
        if (this.signal.aborted) return;

        await this.core.tasks.schedule(Unban, {
            in: '1h',
            data: this.data
        });
    }
}
```

Check `this.signal.aborted` first. A run that shutdown interrupted keeps its job, so scheduling another one would leave you with two.

### Renaming a task

The plugin looks up a stored job's task by key, and the key defaults to the class name. If you rename `Unban` with jobs waiting, no task has their key anymore. The plugin logs a warning and leaves those jobs in your driver. Pass `key` to `@RegisterTask` to keep them working through the rename.

```ts twoslash
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';
// ---cut---
@RegisterTask({ key: 'Unban' })
export class ReleaseBan extends Task<{
    guildId: string;
    userId: string;
}> {
    public async execute(): Promise<void> {
        const { guildId, userId } = this.data;

        this.logger.info(`Releasing ${userId} in ${guildId}`);
    }
}
```

`ReleaseBan` runs the jobs stored for `Unban`, because `key` is what the record holds. Those stored jobs still need to fit the new class's `data`, since the plugin doesn't check a stored record against your type.

### Running more than one copy

The plugin doesn't lock a job, so two copies of your bot that share one store each read it and each run it. Run one copy per store. Separate shard processes break this rule. A rolling deploy does too, when a stored job comes due while both copies are up.

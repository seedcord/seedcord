---
title: Tasks
description: Run a function on a schedule, like a digest every morning or a cleanup every hour, from a folder of task classes in your bot.
---

Some of your bot's work has no command behind it, like a digest every morning or a cleanup every hour. Written by hand, that work was a `setInterval` in `bot.ts`. You started it after login, stopped it before the process exited, logged its errors, and made sure a slow run didn't overlap the next one.

[`@seedcord/plugin-tasks`](ref:plugin-tasks) does that work for you. Each piece of that work is a class in a folder. The plugin loads the folder, starts the tasks once your bot has logged in, and gives running tasks time to finish during shutdown.

<Shell add="@seedcord/plugin-tasks" />

```ts twoslash title="src/bot.ts"
import { Seedcord } from '@seedcord/gateway';
import { Tasks } from '@seedcord/plugin-tasks';
import { GatewayIntentBits } from 'discord.js';

export const seedcord = new Seedcord({
    bot: {
        clientOptions: { intents: [GatewayIntentBits.Guilds] },
        interactions: { path: './handlers' },
        commands: { path: './commands' },
        events: { path: null }
    },
    subscribers: { path: './subscribers' }
}).attach('tasks', Tasks, {
    path: './tasks',
    timezone: 'UTC',
    timeout: 15_000
});

export default seedcord;
```

This sample builds a gateway bot. The same `attach` call works on an http `Seedcord` from `@seedcord/http` that runs on a server. [`Tasks`](ref:plugin-tasks/Tasks) requires a long-running process to hold its timers, so on an http bot for [Cloudflare Workers](/build/workers) the same call is a compile error. With a cast that bypasses the error, `attach` throws `CorePluginScopeMismatch`, which [the plugins page](/plugins#a-plugin-declares-where-it-runs) covers.

{/* prettier-ignore-start */}

| option | required | what it sets |
| --- | --- | --- |
| [`path`](ref:plugin-tasks/TasksOptions.path) | yes | the folder the plugin loads tasks from. A relative path is relative to `root`, and the folder has to be inside it, as [the folder rules](/plugins) describe |
| [`timezone`](ref:plugin-tasks/TasksOptions.timezone) | no | the timezone for every cron task that doesn't set its own. Defaults to the system's timezone |
| [`timeout`](ref:plugin-tasks/TasksOptions.timeout) | no | how long running tasks get to finish during shutdown, in milliseconds. Defaults to 10000 |

{/* prettier-ignore-end */}

`timezone` only takes names from [`IanaTimezone`](ref:plugin-tasks/IanaTimezone), so a value that you read from the environment needs a cast. If that value isn't a real timezone, `attach` throws `PluginTasksInvalidTimezone`.

The plugin reads your stored jobs while the bot starts, even if you only use cron tasks. If your [kv driver](/built-ins/drivers) [can't list its keys](/built-ins#reading-every-record), `init()` throws and the bot doesn't start. [Scheduling jobs](/plugins/tasks-scheduling#keeping-jobs-through-a-restart) covers which drivers work.

## Writing a cron task

Export a class from a file in that folder, extend [`Task`](ref:plugin-tasks/Task), and pass a pattern to [`@RegisterTask`](ref:plugin-tasks/RegisterTask).

```ts twoslash title="src/tasks/Heartbeat.ts"
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';

@RegisterTask('*/5 * * * *')
export class Heartbeat extends Task {
    public async execute(): Promise<void> {
        const { size } = this.core.bot.client.guilds.cache;

        this.logger.info(`Serving ${size} servers`);
    }
}
```

`'*/5 * * * *'` runs `Heartbeat` every five minutes. If a class in the folder doesn't have the decorator, the plugin skips it.

The class name, `Heartbeat`, becomes the task's key, which appears in its logs and its events. If two tasks share a key, startup throws `CoreDuplicateName` with both files.

<Callout type="transport">

The `/gateway` import types `this.core` as the `Core` from `@seedcord/gateway`, which has `bot.client`. An http bot imports `Task` from `@seedcord/plugin-tasks/http`, which types it as the `Core` from `@seedcord/http`.

</Callout>

### Writing a pattern

With a plain cron library, you only found a typo in a pattern when the bot started. `@RegisterTask` checks a literal pattern against [`CronPattern`](ref:plugin-tasks/CronPattern) at compile time and reports the field that's wrong.

```ts twoslash
// @errors: 2345
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';
// ---cut---
@RegisterTask('61 * * * *')
export class Heartbeat extends Task {
    public async execute(): Promise<void> {}
}
```

The minute field takes 0 to 59, so `61` stops the build. A pattern typed as `string`, like one read from `.env`, skips this check. If it's invalid, `init()` throws `PluginTasksInvalidPattern` when the bot starts.

Patterns follow the grammar of [croner](https://croner.56k.guru/usage/pattern/), the cron library the plugin uses. A pattern has five, six, or seven fields. With six or seven, seconds come first, and a seventh field sets the year.

{/* prettier-ignore-start */}

| pattern | when it runs |
| --- | --- |
| `0 9 * * *` | every day at 09:00 |
| `*/30 * * * * *` | every 30 seconds |
| `@daily` | every day at midnight. `@hourly`, `@weekly`, `@monthly`, `@yearly`, `@annually`, and `@midnight` work too |
| `0 18 * * FRI#L` | at 18:00 on the last Friday of the month |

{/* prettier-ignore-end */}

<Callout type="warning">

A pattern with both a day of the month and a day of the week matches either one. `0 12 1 * MON` runs on the 1st _and_ on every Monday. To run only when the 1st is a Monday, write `0 12 1 * +MON`.

</Callout>

If a `string` pattern holds a date, like `2030-01-01T09:00:00`, `init()` throws `PluginTasksDateAsPattern`, because croner reads that as a single date. To run something once, call [`schedule()`](ref:plugin-tasks/Tasks.schedule).

### Setting a timezone

A pattern runs in the timezone of the machine your bot runs on. On a server set to UTC, `0 9 * * *` runs at 09:00 UTC, whatever the time is where your members live. Pass `timezone` to the plugin to set it for every task, and set it on a task that needs a different one.

```ts twoslash title="src/tasks/Digest.ts"
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';
// ---cut---
@RegisterTask('0 9 * * MON', {
    timezone: 'America/New_York',
    key: 'weekly-digest',
    maxRuns: 52
})
export class Digest extends Task {
    public async execute(): Promise<void> {
        this.logger.info('Sending the digest');
    }
}
```

`Digest` runs at 09:00 New York time every Monday, and it stops after 52 runs. A misspelled zone fails to compile.

```ts twoslash
// @errors: 2322
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';
// ---cut---
@RegisterTask('0 9 * * MON', { timezone: 'America/New_Yrok' })
export class Digest extends Task {
    public async execute(): Promise<void> {}
}
```

A timezone typed as `string` skips that check. If it isn't a real timezone, `init()` throws `PluginTasksInvalidTimezone`.

The second argument to `@RegisterTask` takes these options, all optional:

{/* prettier-ignore-start */}

| option | what it sets |
| --- | --- |
| [`key`](ref:plugin-tasks/TaskOptions.key) | the task's key. Defaults to the class name |
| [`timezone`](ref:plugin-tasks/TaskOptions.timezone) | the timezone for this task. Defaults to the plugin's `timezone` |
| [`protect`](ref:plugin-tasks/TaskOptions.protect) | skips a cron or manual run while the previous one is still running. A scheduled job waits for it instead. Defaults to `true` |
| [`paused`](ref:plugin-tasks/TaskOptions.paused) | starts the task paused until you call `this.core.tasks.resume()`. Defaults to `false` |
| [`maxRuns`](ref:plugin-tasks/TaskOptions.maxRuns) | stops the task after this many runs |
| [`startAt`](ref:plugin-tasks/TaskOptions.startAt) | a `Date` or date string. The task doesn't run before it. If a match falls exactly on it, the task runs |
| [`stopAt`](ref:plugin-tasks/TaskOptions.stopAt) | a `Date` or date string. The task doesn't run after it |

{/* prettier-ignore-end */}

croner reads a date string without an offset in the task's timezone. If it can't read `startAt` or `stopAt` as a date, `init()` throws `PluginTasksInvalidDate` with the option's name.

Daylight saving moves some runs. A fixed-time task has one value each for second, minute, and hour, like `30 2 * * *`. When daylight saving ends and 02:30 happens twice, it runs once. When daylight saving starts and 02:30 doesn't exist, it runs at the first time that does.

Every other task, like `*/5 * * * *`, runs in both occurrences of the repeated hour. When daylight saving starts, it skips the times that don't exist.

## What a task can read

`execute()` doesn't take arguments, since everything is on `this`. The plugin builds a new instance for each run, so a field that you set doesn't keep its value for the next run. If a task needs a value between runs, keep it in [`core.kv`](/built-ins).

{/* prettier-ignore-start */}

| member | holds |
| --- | --- |
| [`core`](ref:plugin-tasks/Task.core) | your bot's `Core`, with the client and your plugins |
| [`logger`](ref:plugin-tasks/Task.logger) | a logger that labels each line with the task's key |
| [`key`](ref:plugin-tasks/Task.key) | the task's key |
| [`data`](ref:plugin-tasks/Task.data) | what `schedule()` passed. A cron task has none |
| [`signal`](ref:plugin-tasks/Task.signal) | an `AbortSignal` that aborts when the bot shuts down |
| [`startedAt`](ref:plugin-tasks/Task.startedAt) | when this run started |
| [`trigger`](ref:plugin-tasks/Task.trigger) | a [`TaskTrigger`](ref:plugin-tasks/TaskTrigger) that says what started this run, `'cron'`, `'scheduled'`, or `'manual'` |

{/* prettier-ignore-end */}

## When a run takes too long

Say a task prunes old records every minute, and one run takes 90 seconds. Without a guard, a second prune starts on the same records while the first is still deleting them.

`protect` is on by default for that reason. If the pattern matches, or a handler calls `trigger()`, while the previous run is still running, the plugin skips the new run, logs a warning, and calls [`onOverrun()`](ref:plugin-tasks/Task.onOverrun) if the task defines it.

```ts twoslash title="src/tasks/Prune.ts"
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';
// ---cut---
@RegisterTask('* * * * *')
export class Prune extends Task {
    public async execute(): Promise<void> {
        this.logger.info('Pruning');
    }

    public override async onOverrun(): Promise<void> {
        await this.core.kv
            .collection<number>('skipped')
            .update('prune', (skipped = 0) => skipped + 1);
    }
}
```

`Prune` counts its skipped runs in `onOverrun()`. `this.core` works there too, because the plugin builds that instance from the same context it passes a run. If `onOverrun()` throws, the plugin logs the error, and the task still runs at its next match.

The plugin doesn't skip a [scheduled job](/plugins/tasks-scheduling) of the task. The job waits for the run before it to end, then runs with its data.

Pass `protect: false` only if two runs of the task can safely overlap, since the plugin then starts a run at every match.

## When a task throws

A throw in `execute()` doesn't stop the schedule. The task runs again at its next match. The plugin logs the error, then calls [`onError(error)`](ref:plugin-tasks/Task.onError) if the task defines it, passing the same `Error`. The plugin logs a throw from `onError()` too.

After every run, the plugin publishes `taskRan` on the [bus](/events/bus) with an `outcome` of `'finished'` or `'failed'`. Use `onError()` to clean up after one task, since it runs on the instance that threw. Use `taskRan` for what every task shares, like a report to Sentry, because one subscriber covers them all.

```ts twoslash title="src/subscribers/ReportTaskFailure.ts"
import { Subscribe, Subscriber } from '@seedcord/gateway';
// ---cut-start---
import type {} from '@seedcord/plugin-tasks';
// ---cut-end---

@Subscribe(['taskRan'])
export class ReportTaskFailure extends Subscriber<'taskRan'> {
    public async execute(): Promise<void> {
        const run = this.data;
        //               ^?
        if (run.outcome === 'finished') return;

        this.logger.error(`${run.key} failed`, run.error);
    }
}
```

`error` only exists once `outcome` is `'failed'`, which is why `ReportTaskFailure` checks `outcome` before it reads `run.error`. `jobId` works the same way. It is a string only when `trigger` is `'scheduled'`.

## Controlling a task from a handler

A task that posts to a channel keeps posting while you fix that channel, unless a handler can pause it. A handler reaches the plugin as [`this.core.tasks`](/plugins#reading-it-from-a-handler), since every attached plugin is on `this.core` under its key. From there it can pause a task, run it now, or read its next run time.

```ts twoslash title="src/handlers/PauseDigest.ts"
// ---cut-start---
// @filename: tasks/Digest.ts
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';

@RegisterTask('0 9 * * MON')
export class Digest extends Task {
    public async execute(): Promise<void> {}
}

// @filename: handlers/PauseDigest.ts
import type { Tasks } from '@seedcord/plugin-tasks';

declare module '@seedcord/gateway' {
    interface Core {
        tasks: Tasks;
    }
    interface SlashRegistry {
        'pause-digest': { options: {}; cache: 'cached' };
    }
}
// ---cut-end---
import { SlashHandler, SlashRoute } from '@seedcord/gateway';

import { Digest } from '../tasks/Digest';

@SlashRoute('pause-digest')
export class PauseDigest extends SlashHandler<'pause-digest'> {
    public async execute(): Promise<void> {
        this.core.tasks.pause(Digest);

        await this.reply('The digest is paused.');
    }
}
```

`pause` takes the `Digest` class, imported from the task's file, and looks up its key from the decorator. `this.core.tasks` only has a type once you've run [`seedcord codegen`](/plugins/typing).

{/* prettier-ignore-start */}

| method | what it does |
| --- | --- |
| [`pause(Task)`](ref:plugin-tasks/Tasks.pause) | stops a cron task's pattern. Scheduled jobs and `trigger()` still run the task. After a restart, the pattern runs again |
| [`resume(Task)`](ref:plugin-tasks/Tasks.resume) | starts a task that `pause()` or the `paused` option stopped |
| [`nextRun(Task)`](ref:plugin-tasks/Tasks.nextRun) | returns the next run as a `Date`, or `null` while the task is paused or once it has no runs left |
| [`trigger(Task)`](ref:plugin-tasks/Tasks.trigger) | runs a task now, even while it's paused. If `protect` is on and the task is running, the plugin skips this run and calls `onOverrun()` |
| [`crons()`](ref:plugin-tasks/Tasks.crons) | returns a [`CronStatus`](ref:plugin-tasks/CronStatus) for each cron task, with its `key`, `pattern`, `timezone`, `active`, `busy`, `nextRun`, and `previousRun` |

{/* prettier-ignore-end */}

`pause()` lasts until the process stops, and a save during `seedcord dev` keeps what `pause()` and `resume()` did. Until you call either one, a save applies the `paused` option in the task's file. To keep a task paused after a restart, store a flag in [`core.kv`](/built-ins) and check it at the top of `execute()`.

`pause()`, `resume()`, and `nextRun()` throw `PluginTasksPatternMissing` for a task without a pattern. Each method that takes a class throws `PluginTasksNotLoaded` if the plugin didn't load it from `path`. These methods take tasks without data, so passing a task that declares data fails to compile.

### Checking when a task runs next

`nextRun()` returns a task's next run time as a `Date`. A handler can turn it into a Discord timestamp, and Discord shows it in each reader's own timezone.

```ts twoslash title="src/handlers/DigestNext.ts"
// ---cut-start---
// @filename: tasks/Digest.ts
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';

@RegisterTask('0 9 * * MON')
export class Digest extends Task {
    public async execute(): Promise<void> {}
}

// @filename: handlers/DigestNext.ts
import type { Tasks } from '@seedcord/plugin-tasks';

declare module '@seedcord/gateway' {
    interface Core {
        tasks: Tasks;
    }
    interface SlashRegistry {
        'digest-next': { options: {}; cache: 'cached' };
    }
}
// ---cut-end---
import { SlashHandler, SlashRoute } from '@seedcord/gateway';

import { Digest } from '../tasks/Digest';

@SlashRoute('digest-next')
export class DigestNext extends SlashHandler<'digest-next'> {
    public async execute(): Promise<void> {
        const next = this.core.tasks.nextRun(Digest);

        if (!next) {
            await this.reply('The digest is paused.');
            return;
        }

        const seconds = Math.floor(next.getTime() / 1000);
        await this.reply(`The next digest posts <t:${seconds}:R>.`);
    }
}
```

`nextRun()` returns `null` while the task is paused or once it has no runs left, so check for it before you read the date. To get the next run of every cron task at once, call `crons()` and read each entry's `nextRun`.

## Shutting down

A task that's writing to your database when the bot stops needs that database until it finishes. The plugin's [`dispose()`](ref:plugin-tasks/Tasks.dispose) runs in the `Drain` [shutdown phase](/plugins/lifecycle), before database plugins disconnect. It stops every timer, aborts `this.signal`, and waits for running tasks. If they take longer than `timeout`, seedcord stops waiting and reports [`LifecycleTaskTimeout`](/plugins/lifecycle#the-shutdown-deadline).

Pass `this.signal` to anything slow to end a long request when the bot stops.

```ts twoslash title="src/tasks/SyncStatus.ts"
import { RegisterTask, Task } from '@seedcord/plugin-tasks/gateway';
// ---cut---
@RegisterTask('*/10 * * * *')
export class SyncStatus extends Task {
    public async execute(): Promise<void> {
        const response = await fetch('https://example.com/status', {
            signal: this.signal
        });

        this.logger.info(`Status ${response.status}`);
    }
}
```

When the signal aborts, `fetch` rejects. `SyncStatus` then throws, and the plugin publishes that run as a failed `taskRan` like any other throw.

## Running more than one copy

Each copy of your bot sets its own timers, so `Heartbeat` runs once per copy. If you run separate shard processes, attach this plugin in one copy only. Otherwise every cron task runs once for each process.

[Scheduling jobs](/plugins/tasks-scheduling) picks up from here, with a task that runs once at a later time.

title: Migrations
description: Create and change your database tables with Kysely migrations, so every database gets the same tables, and control when they run.
---

Your bot's tables have to exist on every database it uses, like your laptop, a teammate's machine, and production. If you create them by running `CREATE TABLE` yourself, each database needs the same statements in the same order. If you miss one, your bot fails at the first query that touches a table or column that database doesn't have.

A migration is a file that exports `up`, which makes one change to your database, like creating a table. It can also export `down`, which undoes that change when you roll the migration back. Kysely records each migration it runs in a table in your database. By default, the plugin runs every migration that table doesn't list yet while your bot starts, before any service can query the tables.

```ts twoslash title="src/migrations/001-create-users.ts"
import type { Kysely } from 'kysely';

export async function up(db: Kysely<any>): Promise<void> {
    await db.schema
        .createTable('users')
        .addColumn('id', 'integer', (col) => col.primaryKey())
        .addColumn('discord_id', 'text', (col) =>
            col.notNull().unique()
        )
        .addColumn('streak', 'integer', (col) =>
            col.notNull().defaultTo(0)
        )
        .execute();
}

export async function down(db: Kysely<any>): Promise<void> {
    await db.schema.dropTable('users').execute();
}
```

`up` creates the `users` table, while `down` deletes it. Both take `Kysely<any>` because each migration runs against whatever tables the migrations before it created. On SQLite, an `integer` primary key fills itself in. On Postgres, write `serial` or an identity column for `id`. Your [schema](/plugins/kysely-schema) describes the tables as they are once every migration has run.

## Where to put the files and how to order them

The plugin reads one folder, the `path` under `migrations`, and its subfolders too. A relative `path` is relative to `root` and has to point inside it, as [the folder rules](/plugins) describe. With `root: './src'`, `'./migrations'` means `src/migrations`.

Every code file in that folder has to be a migration. If a file doesn't export `up`, the plugin throws `PluginKyselyInvalidMigrationModule` with the file's path. Keep helper files outside the folder. The plugin reads the same code files as [`importFiles`](ref:utils/importFiles).

<Callout type="warning">

The plugin skips a `.cjs` or `.cts` file without an error, so that migration never runs.

</Callout>

Kysely compares the names of your migrations against the names recorded in its table to find the ones that haven't run. A migration's name is its file name without the folder or the extension, so `001-create-users.ts` is recorded as `001-create-users`. Moving that file into a subfolder keeps its name. If two files in different folders share a name, like `users/001-init.ts` and `guilds/001-init.ts`, the plugin throws `CoreDuplicateName` with both paths.

Kysely sorts the pending migrations by name, by character code, before it runs them. Start each file name with a number like `001-` or a timestamp to set the order. Pad the number with zeros since `10-add-streaks` sorts before `9-create-users`.

The first sample exports `up` and `down` by name. A migration file can also default-export one object holding both functions:

```ts twoslash title="src/migrations/002-add-username.ts"
import type { Kysely } from 'kysely';
// ---cut---
export default {
    async up(db: Kysely<any>): Promise<void> {
        await db.schema
            .alterTable('users')
            .addColumn('username', 'text')
            .execute();
    },
    async down(db: Kysely<any>): Promise<void> {
        await db.schema
            .alterTable('users')
            .dropColumn('username')
            .execute();
    }
};
```

Each file can use either form. If a file has a default export with an `up` function, the plugin reads that one and ignores the file's named exports.

### corrupted migrations: previously executed migration is missing

Kysely throws this error when its table lists a migration name that doesn't match any of your current files:

```txt output
corrupted migrations: previously executed migration 001-create-users is missing
```

The recorded name omits the file extension, so `001-create-users.ts` under `seedcord dev` and `001-create-users.js` in your built bot match the same recorded name. You get the error if you rename or delete a migration file after a database ran it. To fix it, put the file back under its old name.

## When they run

By default the plugin runs every pending migration while the bot starts. If a migration throws, startup stops before your bot reaches its handlers, and the plugin closes the connection. If your deploy waits on the [health path](/build/server#the-health-server), it only gets a healthy answer once the migrations have finished.

`onStartup` changes what runs at that point.

{/* prettier-ignore-start */}

| `onStartup` | what happens while the bot starts |
| --- | --- |
| not set, or `true` | runs every pending migration |
| `false` | skips the migrations |
| a [`MigrationOptions`](ref:plugin-kysely/MigrationOptions) object | runs to the `target`, or in the `direction` and `steps` you pass |

{/* prettier-ignore-end */}

Set it to `false` to choose when migrations run. You then call a [migration method](#running-them-yourself) yourself, like from an owner-only command.

```ts twoslash
import { Kysely } from '@seedcord/plugin-kysely';
import Database from 'better-sqlite3';
import { SqliteDialect } from 'kysely';

// ---cut-start---
import type { Seedcord } from '@seedcord/gateway';

declare const seedcord: Seedcord;
// ---cut-end---
seedcord.attach('db', Kysely, {
    path: './services',
    dialect: () =>
        new SqliteDialect({ database: new Database('bot.db') }),
    migrations: { path: './migrations', onStartup: false }
});
```

With `onStartup: false`, this bot starts on whatever tables the database already has.

Under `seedcord dev`, saving a file in the migrations folder prompts a restart. The plugin ran the migrations when the bot started, so a hot reload would leave the database as it was.

## Running them yourself

You can also run migrations from your own code, like an owner-only command that rolls back the last migration. The plugin has a method for each job, and they work once `init()` has connected. In a handler, you call them on `this.core.db`.

{/* prettier-ignore-start */}

| method | what it does |
| --- | --- |
| [`migrate(options?)`](ref:plugin-kysely/Kysely.migrate) | runs to the latest migration, or to the target or direction you pass |
| [`migrateUp(options?)`](ref:plugin-kysely/Kysely.migrateUp) | runs one pending migration, or `steps` of them |
| [`migrateDown(options?)`](ref:plugin-kysely/Kysely.migrateDown) | reverts the last migration, or the last `steps` of them. It stops at a migration without a `down` |
| [`listMigrations()`](ref:plugin-kysely/Kysely.listMigrations) | every migration, run or pending |
| [`listPendingMigrations()`](ref:plugin-kysely/Kysely.listPendingMigrations) | the ones that haven't run yet |

{/* prettier-ignore-end */}

`migrateUp` and `migrateDown` take a [`StepMigrationOptions`](ref:plugin-kysely/StepMigrationOptions), whose only key is `steps`. `listMigrations()` returns Kysely's `MigrationInfo` objects. Each one's `executedAt` holds a `Date` once that migration has run, and `undefined` before.

`migrate` takes three optional keys. If you pass a `target`, `migrate` ignores `direction` and `steps`.

{/* prettier-ignore-start */}

| key | what it accepts |
| --- | --- |
| `target` | a migration name, or `NO_MIGRATIONS` to revert everything |
| `direction` | `'latest'`, `'up'`, or `'down'`. Defaults to `'latest'` |
| `steps` | how many to run under `'up'` or `'down'`. Defaults to 1 |

{/* prettier-ignore-end */}

`NO_MIGRATIONS` comes from `kysely/migration`.

```ts twoslash
import { NO_MIGRATIONS } from 'kysely/migration';

import type { Kysely } from '@seedcord/plugin-kysely';

declare const db: Kysely;

// ---cut---
await db.migrate({ target: NO_MIGRATIONS });
```

That call runs the `down` of every migration that has one, newest first. Each one only undoes what you wrote in it, so once every `down` deletes what its `up` created, none of your tables are left.

<Callout type="warning">

If a migration in that range is missing its `down`, Kysely skips it and keeps its row in the migrations table, then still rolls back every older one. The next start throws "corrupted migrations: expected previously executed migration" because the recorded list no longer starts with your first migration. Give every migration a `down` before you roll back to `NO_MIGRATIONS`.

</Callout>

Under `'up'` or `'down'`, `steps` has to be a whole number of zero or more. If it's a fraction, a negative number, `NaN`, or `Infinity`, the method throws `PluginKyselyInvalidStepCount`. Zero leaves the database as it is. If you pass any other `direction`, `migrate` throws `PluginKyselyUnknownDirection`.

## When a migration fails

If a migration throws an `Error`, you get that error unchanged, so a failing `CREATE TABLE` shows you the database's own message. For anything else a migration throws, the plugin throws `PluginKyselyNonErrorFailure`. If the migrations folder is missing, you get `CorePathUnreadable` under `seedcord dev` and `CoreDirectoryNotBuilt` in a built bot.

## The rest of the options

{/* prettier-ignore-start */}

| option | what it sets |
| --- | --- |
| `allowUnorderedMigrations` | whether a new migration can sort before one that has already run. Defaults to `false` |
| `migrationTableName` | the table recording which migrations ran. Defaults to `kysely_migration` |
| `migrationLockTableName` | a table Kysely creates beside the migrations table, `kysely_migration_lock` by default |
| `migrationTableSchema` | the schema holding both of those tables, on a database that has schemas, like Postgres |
| `nameComparator` | orders the recorded migrations that share a timestamp when Kysely reads them back from the database. Defaults to `localeCompare`. It never changes the order pending migrations run in |

{/* prettier-ignore-end */}

`allowUnorderedMigrations` matters when two branches each add a migration. Say one branch merges `003-add-streaks` after the database has already run `004-add-guilds`. Unless you set it to `true`, Kysely throws a `corrupted migrations` error before running anything.

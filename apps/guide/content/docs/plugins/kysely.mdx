[`@seedcord/plugin-kysely`](ref:plugin-kysely) opens your database connection and runs your migrations when the bot starts, then closes the connection when it stops. Your queries are plain [Kysely](https://kysely.dev/docs/intro) queries.

You pick the database with a Kysely dialect. The Kysely pages use SQLite through `better-sqlite3`. For another database, install its driver and change `dialect`, as in [the Postgres sample](#other-databases). The migration and schema samples use SQLite column types, so adjust those too.

<Shell add="@seedcord/plugin-kysely kysely better-sqlite3" />

```ts twoslash title="src/bot.ts"
import { Seedcord } from '@seedcord/gateway';
import { Kysely } from '@seedcord/plugin-kysely';
import Database from 'better-sqlite3';
import { GatewayIntentBits } from 'discord.js';
import { SqliteDialect } from 'kysely';

export const seedcord = new Seedcord({
    bot: {
        clientOptions: { intents: [GatewayIntentBits.Guilds] },
        interactions: { path: './handlers' },
        commands: { path: './commands' },
        events: { path: null }
    },
    subscribers: { path: null }
}).attach('db', Kysely, {
    path: './services',
    dialect: () =>
        new SqliteDialect({ database: new Database('bot.db') }),
    migrations: { path: './migrations' }
});

export default seedcord;
```

This sample builds a gateway bot. The same `attach` call works on an http `Seedcord` from `@seedcord/http` that runs on a server. On Cloudflare Workers it's a compile error because the plugin [needs a server](/plugins#a-plugin-declares-where-it-runs). A cast that bypasses the check throws `CorePluginScopeMismatch`.

A relative `path` or `migrations.path` resolves against `root`, and both folders have to be inside it, as [the folder rules](/plugins) describe. `'bot.db'` doesn't follow `root`. `better-sqlite3` opens it relative to the folder you start the bot from.

## Why `dialect` is a function

`seedcord codegen` and `seedcord build` both import `bot.ts` to read your config, and neither one starts the bot. If you passed a dialect object, `new Database('bot.db')` would run on every import. Codegen would then create `bot.db` in whatever folder you ran it from, and an error in your database setup would fail codegen too.

So the plugin calls `dialect()` only in `init()`, when the bot starts.

## The options

{/* prettier-ignore-start */}

| option | required | what it sets |
| --- | --- | --- |
| `path` | yes | the folder that the plugin scans for service classes |
| `dialect` | yes | a function returning the Kysely dialect for your database |
| `migrations` | yes | the folder of your migration files and when they run |
| `kysely` | no | any other Kysely config, like `log` or `plugins` |
| `timeout` | no | how long closing the connection may take during shutdown, in milliseconds. Defaults to 10000 |

{/* prettier-ignore-end */}

The [migrations](/plugins/kysely-migrations) page covers the keys under `migrations`.

## Other databases

Kysely ships dialects like Postgres, MySQL, and SQLite, and [its docs](https://kysely.dev/docs/dialects) list community dialects for other databases. Install the driver that your dialect needs in your project, then build the dialect inside `dialect`.

For Postgres, pass `PostgresDialect` a `pg` pool. Here you read the connection string from `DATABASE_URL` through envapt, which throws if the variable is unset. [Env files and modes](/build/env) covers reading config that way.

```ts twoslash
import { Kysely } from '@seedcord/plugin-kysely';
import { Converters, Envapter } from 'envapt';
import { PostgresDialect } from 'kysely';
import { Pool } from 'pg';

// ---cut-start---
import type { Seedcord } from '@seedcord/gateway';

declare const seedcord: Seedcord;
// ---cut-end---
seedcord.attach('db', Kysely, {
    path: './services',
    dialect: () =>
        new PostgresDialect({
            pool: new Pool({
                connectionString: Envapter.getRequired(
                    'DATABASE_URL',
                    Converters.String
                )
            })
        }),
    migrations: { path: './migrations' }
});
```

To use SQLite without installing a driver, wrap Node's built-in `node:sqlite` with [`nodeSqlite`](ref:plugin-kysely/nodeSqlite). Kysely's `SqliteDialect` expects the API that `better-sqlite3` has, and `nodeSqlite` adapts a `DatabaseSync` to it.

```ts twoslash
import { Kysely, nodeSqlite } from '@seedcord/plugin-kysely';
import { SqliteDialect } from 'kysely';
import { DatabaseSync } from 'node:sqlite';

// ---cut-start---
import type { Seedcord } from '@seedcord/gateway';

declare const seedcord: Seedcord;
// ---cut-end---
seedcord.attach('db', Kysely, {
    path: './services',
    dialect: () =>
        new SqliteDialect({
            database: nodeSqlite(new DatabaseSync('bot.db'))
        }),
    migrations: { path: './migrations' }
});
```

## Startup and shutdown

`init()` calls `dialect()`, opens the first connection, runs your migrations unless you [set `onStartup` to `false`](/plugins/kysely-migrations#when-they-run), then loads every service class from `path`. seedcord doesn't call `dispose()` for a plugin whose `init()` failed, so if any of those steps fails, `init()` closes the connection itself before it rethrows the error. If a migration fails, the bot never reaches its handlers.

If `dialect()` throws, `init()` rethrows that error unchanged, like envapt's error for a missing `DATABASE_URL`. If the first connection fails, `init()` throws `PluginConnectionFailed`. Its message includes the driver's error, like `connect ECONNREFUSED 127.0.0.1:5432` from `pg` when the server isn't running. The full driver error is in its `cause`. `start()` reports it along with any other plugin's failure, as [the lifecycle page](/plugins/lifecycle#when-init-fails) explains.

<Callout type="warning">

Both `path` and the migrations folder have to exist before the first start. If one is missing, `init()` throws `CorePathUnreadable` with the path. A built bot throws `CoreDirectoryNotBuilt` instead because `seedcord build` doesn't find a folder to bundle. An empty folder works in both. Git doesn't track an empty folder, so put a `.gitkeep` in it, which the plugin skips like every dotfile. With `onStartup: false`, only `path` has to exist, and a missing migrations folder throws on your first call to a migration method.

</Callout>

`dispose()` clears the services, then closes the connection through Kysely's `destroy()`, which ends a pool or closes a SQLite file. If `destroy()` fails, `dispose()` throws `PluginDisconnectFailed`.

## The Kysely instance

You keep the queries for one table in a [service](/plugins/kysely-services). For a transaction that writes to two tables, use the Kysely instance directly. That instance is [`connection`](ref:plugin-kysely/Kysely.connection), and in a handler you read it as `this.core.db.connection` once [codegen](/plugins/typing) has typed `db`. If you read it before `init()` connects or after `dispose()`, the read throws `PluginNotReady`.

TypeScript checks the table and column names in those queries against a [schema](/plugins/kysely-schema) you declare yourself.

[`@seedcord/plugin-kysely`](ref:plugin-kysely) opens your database connection and runs your migrations when the bot starts, then closes the connection when it stops. Your queries are plain [Kysely](https://kysely.dev/docs/intro) queries.

You pick the database with a Kysely dialect. This tab uses SQLite through `better-sqlite3`. For another database you only change `dialect`, as in [the Postgres sample](#other-databases).

<Shell add="@seedcord/plugin-kysely kysely better-sqlite3" />

```ts twoslash title="src/bot.ts"
import { Seedcord } from '@seedcord/gateway';
import { Kysely } from '@seedcord/plugin-kysely';
import Database from 'better-sqlite3';
import { GatewayIntentBits } from 'discord.js';
import { SqliteDialect } from 'kysely';

export const seedcord = new Seedcord({
    bot: {
        clientOptions: { intents: [GatewayIntentBits.Guilds] },
        interactions: { path: './handlers' },
        commands: { path: './commands' },
        events: { path: null }
    },
    subscribers: { path: null }
}).attach('db', Kysely, {
    dir: './services',
    dialect: () =>
        new SqliteDialect({ database: new Database('bot.db') }),
    migrations: { dir: './migrations' }
});

export default seedcord;
```

This sample builds a gateway bot. The same `attach` call works on an http `Seedcord` from `@seedcord/http` that runs on a server. On Cloudflare Workers it's a compile error because the plugin [needs a server](/plugins#a-plugin-declares-where-it-runs), and a cast that gets past it throws `CorePluginScopeMismatch`.

You have to pass `dir`, `dialect`, and `migrations`. A relative `dir` or `migrations.dir` resolves against `root`, and both folders have to be inside it, as [the folder rules](/plugins) describe. The `'bot.db'` path is different, since `better-sqlite3` opens it relative to the folder you start the bot from.

## Why `dialect` is a function

`seedcord codegen` and `seedcord build` both import `bot.ts` to read your config, and neither one starts the bot. If you passed a dialect object, `new Database('bot.db')` would run on every import. Codegen would then create `bot.db` in whatever folder you ran it from, and an error in your database setup would fail codegen too.

The plugin calls `dialect()` in `init()` when the bot starts. Codegen and build never call it.

## The options

{/* prettier-ignore-start */}

| option | required | what it sets |
| --- | --- | --- |
| `dir` | yes | the folder that the plugin scans for service classes |
| `dialect` | yes | a function returning the Kysely dialect for your database |
| `migrations` | yes | the folder of your migration files and when they run |
| `kysely` | no | any other Kysely config, like `log` or `plugins` |
| `timeout` | no | how long closing the connection may take during shutdown, in milliseconds. Defaults to 10000 |

{/* prettier-ignore-end */}

The [migrations](/plugins/kysely-migrations) page explains the keys under `migrations`.

## Other databases

Kysely ships dialects like Postgres, MySQL, and SQLite, and [its docs](https://kysely.dev/docs/dialects) list community dialects for other databases. Install the driver that your dialect needs in your project, then build the dialect inside `dialect`.

For Postgres, you pass a `pg` pool, and you read its connection string from the environment. The sample reads `DATABASE_URL` through envapt, which throws if the variable is unset. [Env files and modes](/build/env) covers reading config that way.

```ts twoslash
import { Kysely } from '@seedcord/plugin-kysely';
import { Converters, Envapter } from 'envapt';
import { CompiledQuery, PostgresDialect } from 'kysely';
import { Pool } from 'pg';

// ---cut-start---
import type { Seedcord } from '@seedcord/gateway';

declare const seedcord: Seedcord;
// ---cut-end---
seedcord.attach('db', Kysely, {
    dir: './services',
    dialect: () =>
        new PostgresDialect({
            pool: new Pool({
                connectionString: Envapter.getRequired(
                    'DATABASE_URL',
                    Converters.String
                )
            }),
            onCreateConnection: async (connection) => {
                await connection.executeQuery(
                    CompiledQuery.raw("set time zone 'UTC'")
                );
            }
        }),
    migrations: { dir: './migrations' }
});
```

A Postgres setting like the session time zone only applies to the connection that ran it. Kysely calls `onCreateConnection` for every connection that the pool opens, and it waits for `set time zone 'UTC'` to finish before that connection's first query.

If you'd rather not install a driver for SQLite, you can use Node's built-in `node:sqlite` through [`nodeSqlite`](ref:plugin-kysely/nodeSqlite). Kysely's `SqliteDialect` expects the API that `better-sqlite3` has, and `nodeSqlite` adapts a `DatabaseSync` to it.

```ts twoslash
import { Kysely, nodeSqlite } from '@seedcord/plugin-kysely';
import { SqliteDialect } from 'kysely';
import { DatabaseSync } from 'node:sqlite';

// ---cut-start---
import type { Seedcord } from '@seedcord/gateway';

declare const seedcord: Seedcord;
// ---cut-end---
seedcord.attach('db', Kysely, {
    dir: './services',
    dialect: () =>
        new SqliteDialect({
            database: nodeSqlite(new DatabaseSync('bot.db'))
        }),
    migrations: { dir: './migrations' }
});
```

## Startup and shutdown

`init()` calls `dialect()`, opens the first connection, runs your migrations unless you [set `onStartup` to `false`](/plugins/kysely-migrations#when-they-run), then loads every service class from `dir`. If any of those steps fails, `init()` closes the connection before it rethrows the error because seedcord doesn't call `dispose()` for a plugin whose `init()` failed. If a migration fails, the bot never reaches its handlers.

If `dialect()` throws or that first connection fails, `init()` throws `PluginConnectionFailed`. If `dialect()` threw, the message says so. Otherwise it includes the driver's own message, like `connect ECONNREFUSED 127.0.0.1:5432` from `pg` when the server isn't running. The full driver error is in its `cause`. `start()` reports it along with any other plugin's failure, as [the lifecycle page](/plugins/lifecycle#when-init-fails) explains.

<Callout type="warning">

The `dir` folder and, unless you set `onStartup` to `false`, the migrations folder have to exist before the first start. If one is missing, `init()` throws `CorePathUnreadable` with the path. A built bot throws `CoreDirectoryNotBuilt` instead because `seedcord build` doesn't find a folder to bundle. An empty folder works in both. Git doesn't track an empty folder, so put a `.gitkeep` in it, which the plugin skips like every dotfile. With `onStartup: false`, `init()` never reads the migrations folder and the error appears on your first call to a migration method.

</Callout>

`dispose()` clears the services, then closes the connection through Kysely's `destroy()`, which ends a pool or closes a SQLite file. If `destroy()` fails, `dispose()` throws `PluginDisconnectFailed`.

## The Kysely instance

You keep the queries for one table in a [service](/plugins/kysely-services). For a transaction that writes to two tables, use the Kysely instance directly. That instance is [`connection`](ref:plugin-kysely/Kysely.connection), and in a handler you read it as `this.core.db.connection` once [codegen](/plugins/typing) has typed `db`. If you read it before `init()` connects, the read throws `PluginServicesNotReady`.

TypeScript checks the table and column names in those queries against a [schema](/plugins/kysely-schema) you declare yourself.

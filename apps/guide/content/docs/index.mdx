If you have built a Discord bot, you have written the routing yourself. You switch on the command name, branch on the custom id, write one controller per interaction kind, and extend all of it by hand each time you add a command. I wrote that too, and I copied it into every bot I started.

With plain discord.js, TypeScript can't help with the routing, and it can't help once you're inside the handler either. You register the option yourself, but `getString` still hands back `string | null`. A custom id arrives as a plain string you parse and cast into the thing you encoded. Every read opens with a check whose answer you already know.

Running the bot to test it costs time too. Without hot reload, every tweak means a restart. You'd wait for it to log in, register its commands, and finish every other startup step before you see your change in Discord.

Frameworks do the routing for you. Most put the routing, the checks, and the work in one handler though. Each of those changes for a different reason, so you edit a file holding all three whenever any one of them changes.

I built seedcord to fix all of that, on two principles:

1. seedcord automates what it reliably can, but still leaves you in control.
2. Types cover everything seedcord can work out before your bot runs.

A bot with three commands and a bot with three hundred are written the same way.

seedcord is a TypeScript framework for Discord bots. A bot runs on one of two transports, the two ways Discord can reach it. Both run through [Vite](https://vite.dev).

<Callout type="note">

seedcord is pre-1.0, so a minor version can break. Read the changelog before you bump.

</Callout>

## What seedcord covers

Commands, replies, components, checks, events, plugins, and the dev tooling all come with the framework. You write your bot's features. A route is the id that ties a handler to its command, like `ban`. After `seedcord codegen` writes the types for your commands, a wrong route or option name is a compile error before the bot ever connects.

- **Commands.** Slash commands, subcommands and groups, user and message context menus, autocomplete. A gateway or http server sends the commands it finds to Discord when it starts. A bot on Workers never does, so you deploy its commands with [`seedcord commands deploy`](/tooling/commands#deploy-your-commands).
- **Replying.** Discord accepts [one first response per interaction](https://docs.discord.com/developers/interactions/receiving-and-responding), then edits and follow-ups. seedcord tracks which one you have already sent. If you call the wrong one, it throws an error that says what went wrong and usually which call to use. Throw a [`Notice`](ref:core/Notice) from a handler to stop the command and reply to the user. With `report` set, a `Notice` also logs the error and publishes it for telemetry.
- **Components.** Buttons, select menus, modals, pagination, and more. Discord hands a click back as the `custom_id` string you built, so you parse it yourself. In seedcord you declare the fields once, so the handler gets them back typed. seedcord packs those fields, so more of them fit inside Discord's [100-character limit](https://docs.discord.com/developers/components/reference).
- **Checks.** A gate runs before your handler, and you refuse the call by throwing from it. You put one on a handler with [`@Gated`](ref:gateway/Gated), write your own with [`defineGate`](ref:core/defineGate), and combine them with [`and`](ref:core/and) or [`or`](ref:core/or). seedcord ships a catalog you can import directly, like [cooldowns](/checks/cooldown) and [permission checks](/checks/permissions). [Middleware](/checks/middleware) runs before and after every handler call. A rate limiter counts uses against any key you build.
- **Events.** On gateway, a handler can listen to the events discord.js emits. You can also publish and subscribe to your own events, and that works on http too.
- **Plugins.** A plugin adds a service to your bot, like a database, a cache, or a client for another API. seedcord starts and stops it with the bot, and once `seedcord codegen` has run, you read it from `this.core` in any handler with its type.
- **Tooling.** If you save a handler, the running bot loads it without a restart. `seedcord dev` offers to re-register a command you changed. On http it also opens a tunnel and sets it as your Discord application's endpoint. The same CLI runs codegen, deploys and cleans up your commands, and builds your bot for production. A new project's lint rules flag a handler without a route decorator, like [`@SlashRoute`](ref:core/SlashRoute), in your editor.

## Errors that tell you what to do

Say you deferred, which tells Discord you'll reply later, then called [`reply()`](ref:gateway/RepliableHandler.reply):

```txt output
reply() was called when this interaction was already deferred.
Use edit() to fill the deferred reply. (route slash:ban)
```

Or you packed a component id past what Discord accepts:

```txt output
A customId encoded by "ticket" is 118 characters, but Discord allows
at most 100. Shorten the prefix, or move a field out of the customId.
```

Here you read a custom emoji by name before startup had filled it:

```txt output
Emojis.wave doesn't have a value yet. Emojis fills during startup, but a read
at the top of a file runs before that. Read it inside a handler, or
after start() resolves.
```

discord.js validates a component through shapeshift, whose error nests several levels deep and never says which component or field failed. seedcord reports the one line that matters:

```txt output
ProfileCard at components[0] failed to serialize: need a
ButtonBuilder or ThumbnailBuilder, got nothing.
(route slash:profile)
```

Most errors elsewhere in seedcord follow the same shape and say what happened, where, and what to do about it.

## Your commands type your handlers

You declare an option once, on the command. In the handler, you ask for it by name and get back the type you declared.

```ts twoslash title="src/handlers/Ban.ts"
// @errors: 2345
import { SlashHandler, SlashRoute } from '@seedcord/gateway';

@SlashRoute('ban')
export class Ban extends SlashHandler<'ban'> {
    public async execute(): Promise<void> {
        const target = this.options.getUser('target');
        //    ^?

        await this.reply(`Banned ${target.username}`);

        this.options.getString('resaon');
    }
}
```

The `ban` command, which isn't shown here, declares `target` as required, so it arrives as a plain `User`. If you leave `target` optional, the same call returns `User | null`. Every option you declare is typed. A misspelled name stops the build, like `resaon` on the last line above.

<Callout type="transport">

The sample is gateway, where `getUser` returns a discord.js `User`. On http the same call returns an `APIUser`, which is Discord's raw payload. Both carry `username` and `id`, but only the discord.js one has methods.

</Callout>

Those types come from [`seedcord codegen`](/tooling/codegen), which imports your command files, constructs each command, and writes what the builders produced to `seedcord-gen.ts`. Run it again after you change a command, or say yes when `seedcord dev` offers to re-register.

## What a seedcord project looks like

The generated `seedcord-gen.ts` sits beside your own files, in a tree the setup command creates.

```txt title="my-bot" output
my-bot/
├─ src/
│  ├─ commands/
│  │  └─ Ping.ts
│  ├─ handlers/
│  │  └─ Ping.ts
│  ├─ events/
│  │  └─ Ready.ts
│  ├─ plugins/
│  │  └─ Uptime.ts
│  ├─ bot.ts
│  ├─ index.ts
│  └─ seedcord-gen.ts
├─ seedcord.config.ts
├─ .env
└─ package.json
```

{/* prettier-ignore-start */}

| path | holds |
| --- | --- |
| `src/commands/` | what each command looks like on Discord |
| `src/handlers/` | the code that runs when someone uses a command |
| `src/events/` | handlers for everything else happening in a server, on a gateway bot only |
| `src/plugins/` | a small sample plugin |
| `bot.ts` | your bot's config |
| `seedcord.config.ts` | the CLI's config |
| `seedcord-gen.ts` | the types that the CLI writes |

{/* prettier-ignore-end */}

One command sets this up, along with the tsconfig, lint, and formatter files.

## Gateway and http

You pick one transport when you create the project.

`@seedcord/gateway` holds a websocket connection through the discord.js client, so the events Discord sends about a server reach your bot for the intents you enable.

`@seedcord/http` answers the interaction requests Discord posts to your URL, and Discord posts only interactions there. seedcord checks each signature, rejects a stale or repeated request, and answers the check Discord runs before it accepts your URL. It runs on your own server, in an HTTP route of an app you already have, or on Cloudflare Workers. It doesn't depend on discord.js.

You write commands, handlers, and checks the same way on both. Gateway adds event handlers and hands your handlers discord.js objects. Http hands them Discord's raw payloads. [Gateway or http](/gateway-or-http) helps you pick.

## Your bot runs through Vite

`seedcord dev`, `seedcord codegen`, and `seedcord build` load your bot through Vite. A Vite plugin you return from [`vitePlugins`](/build/vite-plugins) in `seedcord.config.ts` runs in each of them. With `vitePlugins: () => [yaml()]` and `@rollup/plugin-yaml`, for example, a handler can import a `.yaml` file in dev and in the build. `ENV=staging` makes the CLI [read your `.env.staging` files](/build/env#picking-the-mode).

The same [`seedcord build`](/build) makes whatever your host needs:

- A [Node or Bun server](/build/server), or one Bun binary compiled from it.
- A [Cloudflare Worker](/build/workers), for an http bot.
- An [npm package](/build/package) that anyone can install and start.
- A module [inside your own server](/build/embed), for an http bot that shares a process with an app you already run.

## Prerequisites

- **Node 24.22.1+ on the 24.x line, Node 26.12.1+, or Bun 1.4.2+.** Every seedcord package declares its requirements under `engines`.
- **TypeScript.** seedcord uses it heavily. You read and write generics from the first handler onward.
- **discord.js on gateway.** The gateway transport uses the discord.js client, so gateway handlers read discord.js objects. An http bot doesn't depend on discord.js. You write command definitions with `@discordjs/builders` on both transports.

### Does seedcord work with JavaScript?

Not officially. JavaScript works because TypeScript compiles to JavaScript, but you lose a lot of the developer experience that seedcord's types give you. In a `.js` file, call each decorator as a function.

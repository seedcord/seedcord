Discord hands your bot one string when someone clicks, so which button they pressed and what it was pointed at both have to be inside it.

A click arrives as its own interaction carrying that string, the custom id your component minted. [`ButtonHandler`](ref:gateway/ButtonHandler) decodes that id and puts the values on [`this.params`](ref:gateway/ComponentHandler.params).

```ts twoslash title="src/handlers/Appeal.ts"
import {
    ButtonHandler,
    ButtonRoute,
    CustomId
} from '@seedcord/gateway';

// in your project, write this in the component file that builds the button
const AppealId = new CustomId('appeal').snowflake('userId');

@ButtonRoute(AppealId)
export class Appeal extends ButtonHandler<[typeof AppealId]> {
    public async execute(): Promise<void> {
        const { userId } = this.params;
        //      ^?

        await this.reply(`Appeal filed for <@${userId}>.`);
    }
}
```

Pass [`@ButtonRoute`](ref:core/ButtonRoute) the [`CustomId`](ref:custom-id/CustomId) your component used, and list the same one as a tuple in the generic. Passing the decorator one definition and the generic another is a compile error.

A click is an interaction like any other, so every [reply method](/replying) works here.

<Callout type="transport" only="gateway">

A gateway `ButtonHandler` takes a second type argument, discord.js's `CacheType`, which defaults to `'cached'`. That default types `this.event.member` as a `GuildMember`, but seedcord doesn't check it at runtime. A button in a DM doesn't have a member, so pass `CacheType` for a handler that can get one. An http `ButtonHandler` takes only the route tuple.

</Callout>

## Rewriting the source message

A `reply` to a click posts a new message under the old one. The old buttons are still there, so someone can click them again.

[`this.update()`](ref:gateway/ComponentHandler.update) rewrites the message the button came from. It takes the same response shape every reply method takes, so a new `components` list replaces the old buttons.

```ts twoslash
import type { ContainerBuilder } from '@discordjs/builders';
import {
    ButtonHandler,
    ButtonRoute,
    CustomId
} from '@seedcord/gateway';

const AppealId = new CustomId('appeal').snowflake('userId');

declare class ReviewCard {
    constructor(userId: string, status: string);
    readonly component: ContainerBuilder;
}

@ButtonRoute(AppealId)
class Appeal extends ButtonHandler<[typeof AppealId]> {
    public async execute(): Promise<void> {
        // ---cut---
        const { userId } = this.params;

        await this.update({
            components: [
                new ReviewCard(userId, 'under review').component
            ]
        });
        // ---cut-after---
    }
}
```

Discord shows "This interaction failed" on a click that nobody answers within three seconds. For a click that changes nothing on the message, [`this.deferUpdate()`](ref:gateway/ComponentHandler.deferUpdate) answers it and leaves the message unchanged.

<Callout type="transport">
    `update()` resolves to a discord.js `Message` on gateway and an
    `APIMessage` on http.
</Callout>

## One handler, several buttons

Approve and reject sit next to each other on the same message, and one handler can serve both. Pass every id to the decorator, list them in the generic, then branch with [`this.match`](ref:gateway/ComponentHandler.match).

```ts twoslash hovers title="src/handlers/Review.ts"
import {
    ButtonHandler,
    ButtonRoute,
    CustomId
} from '@seedcord/gateway';

const ApproveId = new CustomId('approve').snowflake('userId');
const RejectId = new CustomId('reject')
    .snowflake('userId')
    .str('reason');
// ---cut---
@ButtonRoute(ApproveId, RejectId)
export class Review extends ButtonHandler<
    [typeof ApproveId, typeof RejectId]
> {
    public async execute(): Promise<void> {
        await this.match({
            approve: ({ userId }) =>
                this.update(`Approved <@${userId}>.`),
            reject: ({ userId, reason }) =>
                this.update(`Rejected <@${userId}>. ${reason}`)
        });
    }
}
```

You key each case by its route's prefix, and each one receives that route's own values. `reject` reads a `reason` that `approve` never declared. Both cases pass `update` a plain string, which seedcord wraps in one text component. Leave a case out and the build stops, since the compiler requires one per registered prefix.

Keep two buttons in one handler when both cases need the same code first, like a check that the clicker is staff. Two buttons that share nothing belong in two handlers, where each file holds only the code its own button runs.

<Callout type="warning">

`this.params` is `never` on a handler registered for several routes, since the decoded shape depends on which button someone clicked. `this.match` is the only read there.

Decoding runs once, before any case, so a wire from an [older shape](/components/stale) throws before your code executes.

</Callout>

## Who can click a button

seedcord runs your handler for every click, whoever clicked. On a ticket with a **Close** button, anyone in the channel can close it.

If only one person needs the buttons, send them in [an ephemeral reply](/replying#only-the-person-who-ran-the-command-sees-it), which nobody else can see. To keep the message public, put that person's id in the custom id and compare it to the clicker.

```ts twoslash title="src/handlers/CloseTicket.ts"
import {
    ButtonHandler,
    ButtonRoute,
    CustomId
} from '@seedcord/gateway';
// ---cut-start---
import type { Notice } from '@seedcord/gateway';
declare const NotYourTicket: new () => Notice;
// ---cut-end---

const CloseTicketId = new CustomId('close-ticket').snowflake(
    'ownerId'
);

@ButtonRoute(CloseTicketId)
export class CloseTicket extends ButtonHandler<
    [typeof CloseTicketId]
> {
    public async execute(): Promise<void> {
        const { ownerId } = this.params;
        if (this.user.id !== ownerId) throw new NotYourTicket();

        await this.update('Ticket closed.');
    }
}
```

`NotYourTicket` is a [`Notice`](ref:core/Notice), so seedcord [sends its refusal](/replying/throwing) to the person who clicked and leaves the message as it was.

<Callout type="transport">
    [`this.user`](ref:gateway/RepliableHandler.user) is a discord.js
    `User` on gateway and an `APIUser` on http. Both have `id`.
</Callout>

## When someone clicks twice

Each click runs your handler, so a double click can run it twice at the same moment. That's a problem if the handler gives out a reward or writes to your database.

To stop the second click, call `charge` on [the rate limiter](/checks/rate-limiter) first in `execute()`, with a window that allows one use.

```ts twoslash title="src/handlers/ClaimReward.ts"
import {
    buildKey,
    ButtonHandler,
    ButtonRoute,
    CustomId
} from '@seedcord/gateway';

import type { RateLimitWindow } from '@seedcord/gateway';
// ---cut-start---
declare const rewards: {
    give(rewardId: string, userId: string): Promise<void>;
};
// ---cut-end---

const ClaimRewardId = new CustomId('claim-reward').str('rewardId');
const ONE_CLAIM: RateLimitWindow = { windowMs: 60_000 };

@ButtonRoute(ClaimRewardId)
export class ClaimReward extends ButtonHandler<
    [typeof ClaimRewardId]
> {
    public async execute(): Promise<void> {
        const { rewardId } = this.params;
        const key = buildKey('claim-reward', rewardId);
        const { limited } = await this.core.rateLimiter.charge(
            key,
            ONE_CLAIM
        );
        if (limited) {
            await this.deferUpdate();
            return;
        }

        try {
            await rewards.give(rewardId, this.user.id);
        } catch (error: unknown) {
            await this.core.rateLimiter.reset(key);
            throw error;
        }
        await this.update('Claimed.');
    }
}
```

`charge` counts one click at a time, and `ONE_CLAIM` doesn't set `limit`, which defaults to one use. The second click gets `limited` as `true`, and [`deferUpdate()`](ref:gateway/ComponentHandler.deferUpdate) answers it without changing the message. That click still shows a result, because `update()` on the first click replaces the button with `Claimed.` for everyone. [`buildKey`](ref:core/buildKey) includes `rewardId`, so claiming one reward doesn't block the next one. If `rewards.give` throws, `reset` clears the charge so that the next click can try again.

`ONE_CLAIM` expires after a minute, so it only stops a double click. To stop a second claim for later, keep a record of who claimed in your database, or in [the kv store](/built-ins/) with a driver.

A [`Cooldown`](ref:core/Cooldown) gate also refuses the second click, but it shows a refusal card and counts every use of the route per person, server, or channel. `charge` with your own key limits one reward and answers the second click silently.

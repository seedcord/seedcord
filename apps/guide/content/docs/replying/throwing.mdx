---
title: Refusing a request
description: Refuse a request by throwing a Notice from any handler or helper, so your code stops there and the user sees why.
---

Sometimes you need to stop a command and tell the user why, like when they don't have a profile, aren't allowed to do something, or can't afford it, etc. You do that by throwing a [`Notice`](ref:core/Notice).

seedcord catches that throw at one boundary and sends the reply through the handler, so the class you throw sets the reply's text. A gate throws into the same boundary, and its refusal reaches the user the same way.

## Why not reply and return?

An early return works while the check is in `execute()`.

```ts twoslash
import { SlashHandler, SlashRoute } from '@seedcord/gateway';
// ---cut-start---
declare const profiles: {
    find(id: string): Promise<object | null>;
};
// ---cut-end---

@SlashRoute('ban')
export class Ban extends SlashHandler<'ban'> {
    public async execute(): Promise<void> {
        // ---cut---
        const profile = await profiles.find(this.user.id);
        if (!profile) {
            await this.reply('Create a profile first.');
            return;
        }
        // ---cut-after---
    }
}
```

Throwing does the same in one line.

```ts twoslash
import { Notice } from '@seedcord/gateway';

declare class NoProfile extends Notice {
    constructor();
}
declare const profile: object | null;
// ---cut---
if (!profile) throw new NoProfile();
```

`NoProfile` is a `Notice` like the one in the next section.

Replying with an error message and returning only stops the function you're in. Say your ban handler checks for an open case in a helper. Returning a flag means `execute()` has to check it, and every caller of every helper that can refuse has to check one too. Throw from the helper instead. The handler stops at the line that found the problem, and nothing has to pass a value up a few layers to check it.

## Writing a Notice

You write a refusal as a [`Notice`](ref:core/Notice) subclass.

```ts twoslash title="src/handlers/Ban.ts"
import {
    BuilderComponent,
    Notice,
    SlashHandler,
    SlashRoute
} from '@seedcord/gateway';

import type { ReplyResponse } from '@seedcord/gateway';
// ---cut-start---
declare const cases: { countOpen(id: string): Promise<number> };
// ---cut-end---

class OpenCaseCard extends BuilderComponent<'container'> {
    constructor() {
        super('container');

        this.instance.addTextDisplayComponents((text) =>
            text.setContent(
                '### Cannot ban\nThat user already has an open case.'
            )
        );
    }
}

class OpenCaseExists extends Notice {
    constructor(id: string) {
        super(`user ${id} has an open case`);
    }

    public override render(): ReplyResponse {
        return { components: [new OpenCaseCard().component] };
    }
}

@SlashRoute('ban')
export class Ban extends SlashHandler<'ban'> {
    public async execute(): Promise<void> {
        const target = this.options.getUser('target');
        await this.assertNoOpenCase(target.id);

        await this.reply(`Banned ${target.username}.`);
    }

    private async assertNoOpenCase(id: string): Promise<void> {
        const open = await cases.countOpen(id);
        if (open > 0) throw new OpenCaseExists(id);
    }
}
```

Your logs and your fault reports read the string you pass to `super()`. Since `OpenCaseExists` overrides `render()`, the user never sees that string, so you can put the id there. `render()` builds the reply and returns a [`ReplyResponse`](ref:types/ReplyResponse), the same `{ components }` shape that [`this.reply()`](ref:gateway/RepliableHandler.reply) takes. If you leave `render()` out, seedcord replies with its own refusal card and your `super()` string as the text.

`assertNoOpenCase` refuses on its own. `execute()` calls it and continues, since a refusal never comes back as a return value.

`super()` takes a second argument too, for the error you caught.

```ts twoslash
import { Notice } from '@seedcord/gateway';
// ---cut---
class ProfileUnavailable extends Notice {
    constructor(cause: unknown) {
        super('the profile lookup failed', { cause });
        this.report = true;
    }
}
```

`{ cause }` keeps that error on the throw. With `report` set to `true` there, the fault report prints its stack.

## What each throw produces

{/* prettier-ignore-start */}

| you throw | the user sees | reported |
| --- | --- | --- |
| a `Notice` subclass | what your `render()` returns, or seedcord's refusal card holding your `super()` string | when you set `report` |
| a [`Fault`](ref:core/Fault) | a generic card carrying a tracking uuid | yes, by default |
| a [`Silence`](ref:core/Silence) | nothing | no |
| any other error | that same generic card | yes |

{/* prettier-ignore-end */}

Reported means seedcord logs the throw and puts it on the bus, where a [webhook reporter](/replying/reporting) can send it to a Discord channel. [Faults](/replying/faults) explains the bottom three rows.

## The fields on a Notice, and who sees the card

```ts twoslash
import { Notice } from '@seedcord/gateway';

import type { ReplyResponse } from '@seedcord/gateway';

declare const components: ReplyResponse['components'];

class OpenCaseExists extends Notice {
    // ---cut---
    constructor(id: string) {
        super(`user ${id} has an open case`);

        this.report = true;
        this.ephemeral = false;
        this.summary = 'the target already has an open case';
    }
    // ---cut-after---

    public override render(): ReplyResponse {
        return { components };
    }
}
```

{/* prettier-ignore-start */}

| field | default | what it changes |
| --- | --- | --- |
| `report` | `false` | `true` logs the throw with a uuid and publishes it to the `handledException` bus key |
| `ephemeral` | `true` | `false` shows the reply to everyone in the channel |
| `summary` | unset | a one-line reason the [`or`](ref:core/or) gate lists when every gate inside it refuses |

{/* prettier-ignore-end */}

Only the `or` gate reads `summary`. [Combining gates](/checks/combining) shows where it appears.

<Callout type="warning">

Throwing a custom `Notice` for a real bug shows its card and produces nothing else, because `report` starts `false`. Throw a [`Fault`](ref:core/Fault) when you need the error in your logs or set `report = true` on the `Notice`.

</Callout>

## What render receives

`render()` takes a [`RenderContext`](ref:types/RenderContext). Leave the parameter off when you don't read any of its fields, as `OpenCaseExists` does.

{/* prettier-ignore-start */}

| field | holds |
| --- | --- |
| `ctx.uuid` | the id seedcord logs and reports for this throw |
| `ctx.developerUsername` | `notifications.developerUsername` from your bot config, set on [Faults](/replying/faults). `undefined` when you have not set it |
| `ctx.dispatch` | the [dispatch context](/checks/dispatch-context) the handler and its gates read |

{/* prettier-ignore-end */}

```ts twoslash
import { BuilderComponent, Notice } from '@seedcord/gateway';

import type {
    RenderContext,
    ReplyResponse
} from '@seedcord/gateway';

class TraceCard extends BuilderComponent<'container'> {
    constructor(uuid: string, contact: string) {
        super('container');

        const body = `Tell ${contact} about \`${uuid}\`.`;

        this.instance.addTextDisplayComponents((text) =>
            text.setContent(`### Lookup failed\n${body}`)
        );
    }
}

class LookupFailed extends Notice {
    public constructor() {
        super('the profile lookup failed');
    }

    // ---cut---
    public override render(ctx: RenderContext): ReplyResponse {
        const contact = ctx.developerUsername ?? 'the developer';

        return {
            components: [new TraceCard(ctx.uuid, contact).component]
        };
    }
    // ---cut-after---
}
```

`LookupFailed` builds its `TraceCard` inside `render()`. seedcord calls `render()` each time it shows the refusal, so every reply gets new builders with your bot color read at that moment.

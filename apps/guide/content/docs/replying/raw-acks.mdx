title: Raw acks
description: Call discord.js or Discord's API directly from a handler, and see what seedcord stops tracking when you reply that way.
---

Lets assume you want your ban command to end by asking the server whether to make it permanent, in a poll. Every seedcord reply carries the ComponentsV2 flag, and Discord forbids a poll on a message that has it.

discord.js can still send that poll. On gateway, `this.event` is the discord.js interaction, so `this.event.reply()` reaches Discord the same way `this.reply()` does. However, it skips the ack state that seedcord's own methods keep.

## A raw ack leaves the state stale

The reply sender reads the interaction's state once, when seedcord constructs your handler. That happens before `execute()` runs, and only seedcord's own reply methods move it afterwards. If you send an ack yourself, the copy stays where the last seedcord call left it.

```ts twoslash title="src/handlers/Ban.ts"
import { SlashHandler, SlashRoute } from '@seedcord/gateway';

@SlashRoute('ban')
export class Ban extends SlashHandler<'ban'> {
    public async execute(): Promise<void> {
        await this.event.reply('Banned.');

        await this.edit('Banned, and sessions revoked.');
    }
}
```

Discord accepts the first line. The second throws.

```txt output
edit() was called when nothing has been sent yet.
Send with reply() or defer() first. After that, edit() rewrites it. (route slash:ban)
```

Every later call reads that same stale state, so [`followUp()`](ref:gateway/RepliableHandler.followUp) and [`delete()`](ref:gateway/RepliableHandler.delete) throw too.

## The lint rule

The `edit()` call above throws only when someone runs the command. The lint rule reports the raw call while you write it.

`@seedcord/no-raw-interaction-acks` reports every ack method on a repliable interaction inside a handler or middleware class, plus `respond()` on an autocomplete one. The recommended preset turns it on as an error.

```txt output
src/handlers/Ban.ts
  6:15  error  Reply through this.reply().  @seedcord/no-raw-interaction-acks
```

{/* prettier-ignore-start */}

| discord.js | seedcord |
| --- | --- |
| `reply()` | `this.reply()` |
| `deferReply()` | `this.defer()` |
| `editReply()` | `this.edit()` |
| `followUp()` | `this.followUp()` |
| `update()` | `this.update()` |
| `deferUpdate()` | `this.deferUpdate()` |
| `showModal()` | `this.showModal()` |
| `deleteReply()` | `this.delete()` |
| `fetchReply()` | the message a reply member already returned |
| `respond()` | `this.respond()`, on an autocomplete handler |

{/* prettier-ignore-end */}

The rule resolves the receiver's type, which is how it reports `this.event.reply()` and a local alias alike. It misses a destructured `const { reply } = this.event`, since that call doesn't keep a receiver to resolve.

## When you actually need one

- **An embed or a poll.** The ComponentsV2 flag on every seedcord reply forbids both. `this.event.reply()` sends them on gateway, and `this.api.interactions.reply()` sends them on http.
- **A link with a preview.** Discord doesn't show a preview for a link in a Text Display, so send the link as `content` through the same call. If the link goes to your own site, [`discord-component-embed`](ref:discord-component-embed) replaces that preview with a card you build.
- **A click you collected yourself.** Gateway only. `message.awaitMessageComponent()` hands you a component interaction that never reached seedcord's dispatcher, so no handler and no sender exist for it. That click is its own interaction. Answering it leaves your handler's state where it was. A collector needs a process that stays alive between interactions, but an http bot answers each interaction in its own request.

Apart from a poll and a link preview, seedcord has a replacement for each. Text Display and Container are Discord's replacements for `content` and `embeds` under the flag. seedcord routes a click by its customId to a [`ButtonHandler`](ref:gateway/ButtonHandler), for example, which any process can answer. A collector runs in the process that opened it, so a restart drops every prompt still waiting.

For the interaction that seedcord dispatched, pass the handler's [`sender`](ref:gateway/RepliableHandler.sender) to your helper. It's public. When your helper replies through it, the ack state your handler reads moves too.

```ts twoslash hovers
import { SlashHandler, SlashRoute } from '@seedcord/gateway';
// ---cut---
import type { ReplySender } from '@seedcord/gateway';

async function confirmSaved(sender: ReplySender): Promise<void> {
    await sender.followUp('Saved to the audit log.');
}

@SlashRoute('ban')
export class Ban extends SlashHandler<'ban'> {
    public async execute(): Promise<void> {
        await this.reply('Banned.');

        await confirmSaved(this.sender);
    }
}
```

`confirmSaved` takes the sender because the reply members stay protected. Calling `handler.reply()` from outside the class doesn't compile. The sender carries the same methods.

Since the rule checks code inside handler and middleware classes, answer a collected click from a plain function like this one.

```ts twoslash
import type { Message } from 'discord.js';

export async function acknowledgeClick(
    prompt: Message
): Promise<void> {
    const click = await prompt.awaitMessageComponent({
        time: 30_000
    });

    await click.reply('Got it.');
}
```

seedcord ships [`getConfirmation`](ref:gateway/getConfirmation) for the common confirm-then-act case, which collects the click and answers it for you.

## Calling Discord's API directly

Some Discord calls have nothing to do with replying, like editing a member or adding an emoji to a server.

<Callout type="transport" only="gateway">

`this.core.bot.client` holds the discord.js client, and you make these calls through it.

</Callout>

<Callout type="transport" only="http">

For http, you make these through [`this.api`](ref:http/RepliableHandler.api), a typed REST client over `core.rest` from `@discordjs/core/http-only`, as in `this.api.guilds.editMember()`.

To pass `this.api` to a helper, import its type, `API`, from `@seedcord/http`. `core.rest` works the same way with `REST`. If you install `@discordjs/core` or `@discordjs/rest` yourself, your copy can resolve to a different version, and TypeScript then rejects the value because the two types don't match.

The callbacks on `api.interactions` answer the interaction directly, which leaves the state stale the same way. The lint rule reads discord.js interaction types alone, so those calls pass it.

</Callout>

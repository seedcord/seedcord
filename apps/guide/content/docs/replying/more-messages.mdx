---
title: Deferring and follow-ups
description: Keep an interaction open past Discord's three-second limit, then send more messages and edit or delete them from the same handler.
---

Some handlers need longer than the three seconds Discord allows for a first response. [`this.defer()`](ref:gateway/RepliableHandler.defer) answers inside that with a loading state, which leaves the real reply for later.

```ts twoslash title="src/handlers/Ban.ts"
import { SlashHandler, SlashRoute } from '@seedcord/gateway';
// ---cut-start---

async function countPriorBans(userId: string): Promise<number> {
    return 0;
}
// ---cut-end---

@SlashRoute('ban')
export class Ban extends SlashHandler<'ban'> {
    public async execute(): Promise<void> {
        await this.defer();

        const target = this.options.getUser('target');
        const priors = await countPriorBans(target.id);

        await this.edit(
            `Banned ${target.username}. ${priors} bans before this one.`
        );
    }
}
```

The person who ran the command sees your bot thinking until [`edit()`](ref:gateway/RepliableHandler.edit) runs. Discord expires the interaction token fifteen minutes after the interaction, so every call you make on it has to arrive before then.

## Set ephemeral when you defer

`defer()` takes an `ephemeral` option, and it's on by default. Only the person who ran the command sees the placeholder and the reply that fills it.

```ts twoslash
import { SlashHandler, SlashRoute } from '@seedcord/gateway';

@SlashRoute('ban')
class Ban extends SlashHandler<'ban'> {
    public async execute(): Promise<void> {
        // ---cut---
        await this.defer({ ephemeral: false });
        // ---cut-after---
    }
}
```

`edit()` doesn't take options, so whatever you pass `defer()` is what the reply carries.

## reply() after a deferral throws

The deferral was the initial response. `edit()` rewrites it.

```txt output
reply() was called when this interaction was already deferred.
Use edit() to fill the deferred reply or followUp() for a new
message. (route slash:ban)
```

[`followUp()`](ref:gateway/RepliableHandler.followUp) sends a second message beside the first, which [the next section](#sending-more-messages) covers, and [`delete()`](ref:gateway/RepliableHandler.delete) removes the loading state. [The full table](/replying/ack-states) lists every state and how you reach it.

## Defer before anything slow

[`reply()`](ref:gateway/RepliableHandler.reply) after the three seconds throws Discord's own error, `DiscordAPIError[10062]`, since the interaction is gone by then. seedcord rethrows it untouched, then sends its [error card](/replying/faults) to that same interaction. Discord rejects the card too, and seedcord drops that rejection with a debug line. The person who ran the command sees the interaction fail.

Defer first whenever you can't predict how long the handler takes.

## Sending more messages

Suppose your ban handler revokes the target's sessions after it has already replied "Banned." Telling the caller how that went takes a different call from the first one, and rewriting the message you already sent takes a reference to it.

Once you've replied or deferred, `this.followUp()` sends another message. Every one of `reply()`, `followUp()`, and `edit()` resolves to the message it wrote. Pass one back to `edit()` to rewrite it.

```ts twoslash title="src/handlers/Ban.ts"
import { SlashHandler, SlashRoute } from '@seedcord/gateway';

async function revokeSessions(userId: string): Promise<number> {
    return 0;
}
// ---cut---
@SlashRoute('ban')
export class Ban extends SlashHandler<'ban'> {
    public async execute(): Promise<void> {
        const target = this.options.getUser('target');

        await this.reply(`Banned ${target.username}.`);

        const progress = await this.followUp('Revoking sessions.');
        const revoked = await revokeSessions(target.id);

        await this.edit(progress, `Revoked ${revoked} sessions.`);
    }
}
```

`edit()` with one argument rewrites the first reply. `edit(message, response)` rewrites the message you pass.

<Callout type="transport">
    That message is a discord.js `Message` on gateway and an
    `APIMessage` on http. Passing it back to `edit()` or `delete()`
    works on both.
</Callout>

## Targets have to come from this interaction

Discord lets an interaction's token edit and delete only the messages sent with that token. seedcord stores the id of every message it sends, and a targeted `edit()` or `delete()` checks the id against that list before calling Discord.

```txt output
edit() was passed message 1287, which this interaction did not send.
Pass a message this interaction sent, returned by reply(),
followUp(), edit(), or update(). (route slash:ban)
```

`delete()` checks the same list. Without an argument it removes the first reply. `delete(message)` removes the one you pass, so that id leaves the list and a later edit of it throws.

```ts twoslash
import { SlashHandler, SlashRoute } from '@seedcord/gateway';

@SlashRoute('ban')
class Ban extends SlashHandler<'ban'> {
    public async execute(): Promise<void> {
        // ---cut---
        const notice = await this.followUp('Working.');

        await this.delete(notice);
        await this.delete();
        // ---cut-after---
    }
}
```

## send() picks the method for you

[`this.send()`](ref:gateway/RepliableHandler.send) works from every state, so it never throws [the wrong-state error](/replying/ack-states) that the other methods throw.

{/* prettier-ignore-start */}

| state | send() calls |
| --- | --- |
| nothing sent yet | `reply()` |
| deferred a reply | `edit()`, filling the placeholder |
| deferred an update | `followUp()` |
| already replied | `followUp()` |

{/* prettier-ignore-end */}

`ephemeral` and `silent` apply only when `send()` creates a message. On the `edit()` row it drops them, since `edit()` doesn't take options.

Use `send()` in code that runs from more than one state, like a helper that a deferring handler and a replying handler both call.

If you already know the state, call `reply()` or `edit()` directly. Each one throws on a state it can't run in, so a misplaced `defer()` surfaces as a throw from `reply()`.

After a deferral, `send()` edits the placeholder. Call `followUp()` for a new message.
